# 캐싱

## 이번 장에서 배울 것

이번 장에서는 Spring Boot에서 캐시를 사용하는 기본 방법을 배운다.

캐시는 같은 계산이나 같은 조회를 매번 반복하지 않도록 결과를 잠시 저장해 두는 기술이다. 잘 쓰면 응답 속도가 빨라지고 DB 부하가 줄어든다. 하지만 잘못 쓰면 오래된 데이터를 보여주거나 장애를 숨기는 문제가 생긴다.

이번 장의 목표는 캐시 애너테이션을 외우는 것이 아니라, "언제 캐시해야 하고 언제 캐시하면 안 되는지"를 판단하는 감각을 잡는 것이다.

## 캐시는 왜 필요한가

예를 들어 할 일 목록 API에서 매번 다음 작업을 한다고 생각해 보자.

1. DB에 접속한다.
2. 사용자 정보를 조회한다.
3. 권한을 확인한다.
4. 자주 바뀌지 않는 설정 값을 읽는다.
5. 응답을 만든다.

이 중 어떤 값은 매 요청마다 새로 읽을 필요가 없다. 예를 들어 카테고리 목록, 공통 코드, 상품 상세의 일부 정보, 외부 API에서 가져온 환율 정보는 잠깐 저장해 두고 다시 써도 된다.

캐시는 이런 상황에서 유용하다.

```text
느린 작업의 결과를 저장한다.
같은 요청이 다시 오면 저장된 결과를 바로 돌려준다.
```

## Spring의 Cache Abstraction

Spring은 캐시 저장소를 직접 강제하지 않는다. 대신 공통 추상화를 제공한다.

대표 인터페이스는 다음 두 가지다.

- `Cache`: 하나의 캐시 공간
- `CacheManager`: 여러 캐시를 관리하는 관리자

개발자는 `@Cacheable`, `@CachePut`, `@CacheEvict` 같은 애너테이션을 사용한다. 실제 저장소는 메모리, Caffeine, Redis, JCache 구현체 등으로 바꿀 수 있다.

Spring Boot는 `@EnableCaching`을 사용하면 캐시 인프라를 자동 설정한다.

## 의존성 추가

Gradle 예시:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-cache'
}
```

처음에는 별도 캐시 라이브러리를 추가하지 않아도 된다. 그러면 Spring Boot는 단순한 메모리 기반 캐시를 사용한다. 이 방식은 학습용으로는 좋지만 운영용으로는 권장하지 않는다.

## 캐싱 켜기

캐싱을 사용하려면 설정 클래스에 `@EnableCaching`을 붙인다.

```java
package com.example.todo.config;

import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.Configuration;

@Configuration
@EnableCaching
public class CacheConfig {
}
```

공식 문서에서는 `main` 애플리케이션 클래스에 무조건 붙이기보다 별도 설정 클래스로 분리하는 편을 권한다. 테스트에서 캐시가 항상 켜져 있으면 테스트 결과가 헷갈릴 수 있기 때문이다.

## `@Cacheable`

`@Cacheable`은 "캐시에 값이 있으면 메서드를 실행하지 않고 캐시 값을 돌려주라"는 뜻이다.

```java
package com.example.todo.service;

import org.springframework.cache.annotation.Cacheable;
import org.springframework.stereotype.Service;

@Service
public class CategoryService {

    @Cacheable("categories")
    public List<String> findDefaultCategories() {
        simulateSlowQuery();
        return List.of("WORK", "STUDY", "LIFE");
    }

    private void simulateSlowQuery() {
        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

첫 호출은 1초 정도 걸린다. 두 번째 호출부터는 캐시에서 바로 가져온다.

## 캐시 이름과 키

캐시 이름은 저장 공간의 이름이다.

```java
@Cacheable("todos")
public TodoResponse findById(Long id) {
    ...
}
```

기본 키는 메서드 파라미터를 바탕으로 만들어진다. 파라미터가 하나라면 그 값이 키가 된다.

직접 키를 정할 수도 있다.

```java
@Cacheable(cacheNames = "todos", key = "#id")
public TodoResponse findById(Long id) {
    ...
}
```

여러 파라미터를 조합할 수도 있다.

```java
@Cacheable(cacheNames = "searchTodos", key = "#userId + ':' + #keyword")
public List<TodoResponse> search(Long userId, String keyword) {
    ...
}
```

## `@CacheEvict`

캐시에서 가장 중요한 것은 지우는 시점이다. 데이터가 바뀌었는데 캐시를 지우지 않으면 사용자는 오래된 값을 본다.

```java
import org.springframework.cache.annotation.CacheEvict;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class TodoService {

    @Transactional
    @CacheEvict(cacheNames = "todos", key = "#id")
    public void updateTitle(Long id, String title) {
        Todo todo = todoRepository.findById(id)
                .orElseThrow();
        todo.changeTitle(title);
    }
}
```

업데이트가 끝나면 해당 `id`의 캐시를 제거한다. 다음 조회 때는 DB에서 다시 읽고 새 값이 캐시에 저장된다.

## `@CachePut`

`@CachePut`은 메서드를 항상 실행하고, 그 결과를 캐시에 다시 저장한다.

```java
@CachePut(cacheNames = "todos", key = "#result.id")
public TodoResponse save(CreateTodoRequest request) {
    Todo todo = todoRepository.save(new Todo(request.title()));
    return TodoResponse.from(todo);
}
```

초보 단계에서는 `@Cacheable`과 `@CacheEvict`만 먼저 익혀도 충분하다. `@CachePut`은 캐시 갱신 전략이 분명할 때 사용한다.

## Caffeine 사용하기

Caffeine은 JVM 안에서 사용하는 고성능 로컬 캐시다. 단일 애플리케이션에서는 간단하고 빠르다.

Gradle:

```groovy
dependencies {
    implementation 'com.github.ben-manes.caffeine:caffeine'
}
```

`application.yml`:

```yaml
spring:
  cache:
    type: caffeine
    cache-names:
      - categories
      - todos
    caffeine:
      spec: maximumSize=1000,expireAfterWrite=10m
```

이 설정은 최대 1000개까지 저장하고, 쓴 지 10분이 지나면 만료한다.

## Redis 캐시

여러 서버 인스턴스가 같은 캐시를 공유해야 한다면 Redis를 많이 사용한다.

```yaml
spring:
  cache:
    type: redis
  data:
    redis:
      host: localhost
      port: 6379
```

Redis 캐시는 서버를 여러 대 띄워도 같은 캐시 저장소를 본다는 장점이 있다. 대신 네트워크 비용과 직렬화 설정을 고려해야 한다.

## 캐시 대상 선택 기준

좋은 캐시 대상:

- 자주 조회된다.
- 계산이나 조회 비용이 크다.
- 잠깐 오래된 값이 보여도 큰 문제가 없다.
- 변경 빈도가 낮다.
- 키를 명확히 만들 수 있다.

좋지 않은 캐시 대상:

- 사용자마다 민감하게 달라지는 권한 정보
- 즉시 일관성이 중요한 결제, 재고, 잔액
- 변경이 매우 잦은 데이터
- 키가 불명확한 검색 결과
- 캐시를 지우는 시점을 설명할 수 없는 데이터

## 캐시와 트랜잭션

캐시 제거와 DB 변경이 함께 있을 때는 주의해야 한다.

```java
@Transactional
@CacheEvict(cacheNames = "todos", key = "#id")
public void update(Long id, String title) {
    ...
}
```

트랜잭션이 롤백되었는데 캐시가 먼저 지워지거나, 반대로 DB는 바뀌었는데 캐시가 남는 상황을 조심해야 한다. 중요한 데이터는 캐시 동작을 테스트로 확인하는 편이 좋다.

## 테스트에서 캐시 조심하기

캐시가 켜진 테스트는 순서에 따라 결과가 달라질 수 있다.

테스트에서 캐시를 끄고 싶다면 테스트 프로필에 다음처럼 둘 수 있다.

```yaml
spring:
  cache:
    type: none
```

또는 테스트마다 `CacheManager`를 주입받아 캐시를 비울 수 있다.

## 자주 하는 실수

### 캐시는 성능을 무조건 좋게 만든다고 생각한다

캐시도 비용이 있다. 메모리를 쓰고, 만료 정책을 관리해야 하며, 오래된 데이터 문제가 생긴다.

### 삭제 전략 없이 `@Cacheable`만 붙인다

캐시는 저장보다 삭제가 어렵다. 데이터를 바꾸는 API가 있다면 어떤 캐시를 지울지 반드시 정해야 한다.

### 운영에서 simple 캐시를 그대로 쓴다

Spring Boot의 simple 캐시는 시작하기에는 좋지만 운영 요구에 맞는 만료, 크기 제한, 분산 처리를 제공하지 않는다.

### 사용자별 데이터를 같은 키로 캐시한다

사용자 ID가 키에 포함되지 않으면 다른 사용자의 데이터를 볼 수 있는 심각한 문제가 생길 수 있다.
