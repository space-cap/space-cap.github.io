# 클라우드 배포 개요

## 이번 장에서 배울 것

이 장에서는 Spring Boot 애플리케이션을 클라우드에 배포하는 선택지를 큰 그림으로 정리한다.

배포 방식은 하나가 아니다. 팀의 규모, 운영 역량, 비용, 트래픽, 장애 대응 방식에 따라 선택이 달라진다.

## 배포의 기본 목표

배포는 단순히 서버에 파일을 올리는 일이 아니다.

운영 배포에는 다음이 필요하다.

- 애플리케이션 실행
- 설정과 secret 주입
- 로그 수집
- 메트릭 수집
- health check
- 장애 시 재시작
- 무중단 또는 최소 중단 배포
- rollback
- 보안 업데이트

어떤 플랫폼을 쓰든 이 질문에 답할 수 있어야 한다.

## VM 배포

가장 전통적인 방식은 VM에 JAR를 배포하는 것이다.

예:

```text
EC2, Compute Engine, Azure VM
```

흐름:

```text
JAR 빌드 -> 서버 복사 -> java -jar 실행 -> systemd로 관리
```

장점:

- 구조가 이해하기 쉽다.
- 기존 서버 운영 방식과 비슷하다.
- 작은 서비스에 충분할 수 있다.

단점:

- 서버 패치와 런타임 설치를 직접 관리해야 한다.
- 서버마다 환경 차이가 생길 수 있다.
- 스케일링과 롤백 자동화가 약할 수 있다.

## 컨테이너 기반 배포

Docker 이미지로 패키징한 뒤 컨테이너 플랫폼에 배포하는 방식이다.

예:

```text
AWS ECS
Google Cloud Run
Azure Container Apps
Kubernetes
```

흐름:

```text
이미지 빌드 -> Registry push -> 플랫폼 배포
```

장점:

- 실행 환경을 이미지로 고정할 수 있다.
- 배포와 롤백이 이미지 태그 중심으로 명확하다.
- 스케일링과 health check 연동이 좋다.

단점:

- 이미지 빌드와 registry 관리가 필요하다.
- 컨테이너 네트워크와 볼륨 개념을 알아야 한다.

## PaaS 배포

PaaS는 애플리케이션 코드를 올리면 플랫폼이 실행 환경을 많이 관리해주는 방식이다.

예:

```text
Heroku 계열 플랫폼
Cloud Foundry
Render
Railway
Fly.io
```

장점:

- 시작이 빠르다.
- 인프라 관리 부담이 작다.
- 작은 팀에 좋다.

단점:

- 플랫폼 제약이 있다.
- 복잡한 네트워크나 인프라 요구에 한계가 있을 수 있다.
- 비용 구조를 잘 봐야 한다.

## Kubernetes

Kubernetes는 컨테이너 오케스트레이션 플랫폼이다.

장점:

- 대규모 서비스 운영에 강하다.
- 선언적 배포, rolling update, self-healing, autoscaling 지원
- 생태계가 풍부하다.

단점:

- 학습 비용이 높다.
- 운영 복잡도가 크다.
- 작은 프로젝트에는 과할 수 있다.

Spring Boot 애플리케이션을 Kubernetes에 배포할 때 중요한 요소:

- Docker 이미지
- Deployment
- Service
- ConfigMap
- Secret
- readiness/liveness probe
- resource requests/limits
- Horizontal Pod Autoscaler

## Cloud Run 같은 서버리스 컨테이너

서버리스 컨테이너 플랫폼은 컨테이너 이미지를 올리면 요청에 따라 실행과 스케일링을 관리해준다.

장점:

- 서버 관리 부담이 작다.
- 트래픽이 없을 때 비용을 줄일 수 있다.
- HTTP API 배포가 간단하다.

주의할 점:

- 콜드 스타트
- 요청 처리 시간 제한
- 백그라운드 작업 제약
- stateless 설계 필요

Spring Boot는 JVM 시작 시간이 있기 때문에 Native Image나 CDS 같은 최적화를 함께 고려할 수 있다.

## 데이터베이스 배포

애플리케이션보다 DB 운영이 더 중요할 때가 많다.

초보자에게는 관리형 DB를 추천한다.

예:

```text
Amazon RDS
Google Cloud SQL
Azure Database for PostgreSQL
```

관리형 DB는 백업, 패치, 장애 조치, 모니터링을 플랫폼이 많이 도와준다.

직접 DB를 컨테이너로 운영하는 것은 학습에는 좋지만 운영에서는 신중해야 한다.

## CI/CD 흐름

일반적인 배포 파이프라인:

```text
코드 push
-> 테스트 실행
-> JAR 또는 이미지 빌드
-> 이미지 registry push
-> 배포
-> health check
-> 모니터링
```

배포 자동화에서 중요한 것:

- 테스트 실패 시 배포 중단
- 이미지 태그 추적
- 설정과 secret 분리
- rollback 방법
- 배포 후 health check

## 선택 기준

간단한 기준:

| 상황 | 추천 |
| --- | --- |
| 개인 학습 | 로컬 JAR, Docker Compose |
| 작은 사이드 프로젝트 | PaaS, 서버리스 컨테이너 |
| 작은 회사 API | VM, ECS, Cloud Run |
| 여러 서비스와 팀 | Kubernetes 또는 관리형 컨테이너 플랫폼 |
| DB 운영 경험 부족 | 관리형 DB |

정답은 없다. 운영할 사람이 이해하고 책임질 수 있는 수준의 복잡도를 선택하는 것이 중요하다.

## 자주 하는 실수

### 처음부터 Kubernetes로 간다

학습 목적이 아니라면 작은 서비스에는 과할 수 있다.

### DB를 애플리케이션 컨테이너와 같은 방식으로 가볍게 본다

DB는 백업, 복구, 업그레이드, 데이터 무결성이 중요하다.

### rollback 계획이 없다

배포는 실패할 수 있다. 되돌릴 수 있어야 한다.
