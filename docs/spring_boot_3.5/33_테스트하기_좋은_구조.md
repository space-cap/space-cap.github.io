# 테스트하기 좋은 구조

## 이번 장에서 배울 것

이 장에서는 테스트하기 좋은 Spring Boot 애플리케이션 구조를 배운다.

테스트 도구를 많이 알아도 코드 구조가 나쁘면 테스트는 어렵다. 반대로 구조가 좋으면 테스트는 자연스럽게 따라온다.

## 테스트하기 어려운 코드의 특징

테스트하기 어려운 코드는 보통 이런 모습을 가진다.

- Controller에 비즈니스 로직이 많다.
- Service가 외부 API, DB, 시간, 랜덤값에 직접 강하게 의존한다.
- 정적 메서드와 전역 상태가 많다.
- 하나의 메서드가 너무 많은 일을 한다.
- 테스트 데이터 준비가 복잡하다.
- 성공 케이스만 고려하고 실패 경로가 숨겨져 있다.

테스트하기 어렵다는 것은 보통 변경하기도 어렵다는 뜻이다.

## 계층을 분리한다

기본 계층은 다음처럼 나눌 수 있다.

```text
Controller -> Service -> Repository
```

각 역할:

- Controller: HTTP 요청과 응답
- Service: 비즈니스 규칙과 트랜잭션
- Repository: 데이터 접근

이 분리가 잘 되어 있으면 테스트도 자연스럽게 나뉜다.

```text
Controller 테스트: @WebMvcTest
Service 테스트: 단위 테스트 또는 @SpringBootTest 일부
Repository 테스트: @DataJpaTest
전체 흐름 테스트: @SpringBootTest
```

## Controller를 얇게 유지한다

Controller는 HTTP 경계만 다루는 것이 좋다.

좋은 예:

```java
@RestController
@RequestMapping("/todos")
public class TodoController {

    private final TodoService todoService;

    public TodoController(TodoService todoService) {
        this.todoService = todoService;
    }

    @PostMapping
    public TodoResponse create(@Valid @RequestBody TodoCreateRequest request) {
        return todoService.create(request);
    }
}
```

Controller가 얇으면 `@WebMvcTest`에서 요청과 응답만 깔끔하게 검증할 수 있다.

## 비즈니스 규칙은 Service 또는 도메인으로 옮긴다

나쁜 예:

```java
@PostMapping("/{id}/complete")
public TodoResponse complete(@PathVariable Long id) {
    Todo todo = todoRepository.findById(id).orElseThrow();
    if (todo.isCompleted()) {
        throw new IllegalStateException("이미 완료된 할 일입니다.");
    }
    todo.complete();
    return TodoResponse.from(todo);
}
```

Controller가 Repository와 비즈니스 규칙까지 알고 있다.

좋은 예:

```java
@PostMapping("/{id}/complete")
public TodoResponse complete(@PathVariable Long id) {
    return todoService.complete(id);
}
```

Service:

```java
@Transactional
public TodoResponse complete(Long id) {
    Todo todo = todoRepository.findById(id)
            .orElseThrow(() -> new TodoNotFoundException(id));
    todo.complete();
    return TodoResponse.from(todo);
}
```

Entity:

```java
public void complete() {
    if (completed) {
        throw new IllegalStateException("이미 완료된 할 일입니다.");
    }
    this.completed = true;
}
```

규칙이 도메인 객체 안에 있으면 순수 단위 테스트로도 검증할 수 있다.

## 시간을 주입한다

테스트하기 어려운 코드:

```java
this.createdAt = LocalDateTime.now();
```

현재 시간이 코드 안에 박혀 있으면 테스트 결과가 매번 달라진다.

개선 방향:

```java
import java.time.Clock;
import java.time.LocalDateTime;

@Service
public class TodoService {

    private final Clock clock;

    public TodoService(Clock clock) {
        this.clock = clock;
    }

    public Todo create(String title) {
        return new Todo(title, LocalDateTime.now(clock));
    }
}
```

설정:

```java
@Configuration
public class TimeConfig {

    @Bean
    public Clock clock() {
        return Clock.systemDefaultZone();
    }
}
```

테스트에서는 고정 시간을 넣을 수 있다.

```java
Clock fixedClock = Clock.fixed(
        Instant.parse("2026-05-19T00:00:00Z"),
        ZoneOffset.UTC
);
```

## 외부 API는 인터페이스로 감싼다

외부 API를 직접 호출하면 테스트가 느리고 불안정해진다.

인터페이스:

```java
public interface TodoNotifier {

    void notifyCreated(Long todoId);
}
```

운영 구현체:

```java
@Component
public class HttpTodoNotifier implements TodoNotifier {

    @Override
    public void notifyCreated(Long todoId) {
        // 외부 API 호출
    }
}
```

테스트에서는 가짜 구현체나 Mockito를 사용할 수 있다.

이렇게 경계를 만들면 Service 테스트가 외부 네트워크에 흔들리지 않는다.

## 테스트 데이터 빌더

테스트 데이터 생성 코드가 반복되면 빌더나 팩터리 메서드를 만든다.

```java
public class TodoTestData {

    public static Todo todo(String title) {
        return new Todo(title);
    }

    public static Todo completedTodo(String title) {
        Todo todo = new Todo(title);
        todo.complete();
        return todo;
    }
}
```

테스트:

```java
Todo todo = TodoTestData.todo("Spring Boot 공부");
```

테스트 본문에서 중요한 검증만 보이게 만드는 것이 좋다.

## 테스트 피라미드

테스트는 균형이 중요하다.

```text
많이 작성: 단위 테스트
적당히 작성: 슬라이스 테스트
조금 작성: 전체 통합 테스트
```

단위 테스트는 빠르고 싸다. 전체 통합 테스트는 현실에 가깝지만 느리고 관리 비용이 크다.

좋은 프로젝트는 빠른 테스트가 넓게 깔려 있고, 중요한 시나리오에 통합 테스트가 있다.

## 무엇을 테스트하지 않을까?

모든 코드를 테스트할 필요는 없다.

우선순위가 높은 것:

- 비즈니스 규칙
- 돈, 재고, 권한, 상태 변경
- 복잡한 조건문
- 직접 작성한 쿼리
- 장애가 나면 큰 문제가 되는 흐름

우선순위가 낮은 것:

- 단순 getter/setter
- 프레임워크가 이미 보장하는 동작
- 너무 단순한 위임 코드

테스트는 개수를 늘리는 게임이 아니라 위험을 줄이는 작업이다.

## 좋은 테스트의 조건

좋은 테스트는 다음 특성을 가진다.

- 빠르다.
- 독립적이다.
- 반복 실행해도 결과가 같다.
- 실패 이유가 명확하다.
- 구현 세부사항보다 행동을 검증한다.
- 읽는 사람이 의도를 이해할 수 있다.

특히 독립성이 중요하다. 테스트 실행 순서에 따라 성공과 실패가 달라지면 신뢰하기 어렵다.

## 자주 하는 실수

### 테스트가 구현 세부사항에 너무 묶인다

내부 메서드 호출 횟수보다 최종 행동을 검증하는 것이 더 좋은 경우가 많다.

### 테스트 데이터가 서로 공유된다

테스트는 독립적이어야 한다. 공유 상태를 줄이고, 테스트마다 필요한 데이터를 준비한다.

### 느린 테스트만 많다

모든 테스트가 Spring Context를 띄우면 피드백이 늦어진다. 단위 테스트를 충분히 둔다.

## 확인 문제

1. Controller를 얇게 유지하면 테스트에 어떤 장점이 있는가?
2. 현재 시간을 직접 호출하는 코드가 테스트하기 어려운 이유는 무엇인가?
3. 외부 API를 인터페이스로 감싸면 어떤 장점이 있는가?
4. 테스트 피라미드에서 가장 많이 작성해야 하는 테스트는 무엇인가?
