# 모니터링과 메트릭

## 이번 장에서 배울 것

이 장에서는 메트릭과 모니터링의 기본을 배운다.

로그는 어떤 일이 일어났는지 자세히 알려준다. 메트릭은 애플리케이션의 상태를 숫자로 보여준다. 운영자는 이 숫자를 보고 서비스가 느려졌는지, 오류가 늘었는지, 메모리가 부족한지 판단한다.

## 메트릭이란 무엇인가

메트릭은 시간에 따라 수집되는 숫자 데이터다.

예:

- HTTP 요청 수
- HTTP 응답 시간
- 500 오류 수
- JVM 메모리 사용량
- CPU 사용량
- DB 커넥션 풀 사용량
- 스레드 수
- GC 횟수와 시간

메트릭은 "지금 서비스가 괜찮은가"를 빠르게 보여준다.

## Micrometer

Spring Boot Actuator는 Micrometer를 기반으로 메트릭을 다룬다.

Micrometer는 메트릭 facade다. 애플리케이션 코드는 Micrometer API로 메트릭을 기록하고, 실제 저장소는 Prometheus, Datadog, OTLP, Graphite 같은 시스템으로 바꿀 수 있다.

즉 Micrometer는 다음 사이의 중간 계층이다.

```text
Spring Boot Application -> Micrometer -> Prometheus/Datadog/OTLP/...
```

## 기본 메트릭 확인

Actuator 의존성이 있으면 기본 메트릭을 볼 수 있다.

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,metrics
```

메트릭 목록:

```bash
curl http://localhost:8080/actuator/metrics
```

특정 메트릭:

```bash
curl http://localhost:8080/actuator/metrics/http.server.requests
```

자주 보는 메트릭:

```text
http.server.requests
jvm.memory.used
jvm.threads.live
process.cpu.usage
system.cpu.usage
hikaricp.connections.active
```

DB 커넥션 풀 메트릭은 HikariCP를 사용할 때 유용하다.

## Prometheus 연동

Prometheus는 메트릭 수집 시스템이다. Spring Boot에서 Prometheus 형식으로 메트릭을 노출하려면 의존성을 추가한다.

```groovy
dependencies {
    implementation 'io.micrometer:micrometer-registry-prometheus'
}
```

설정:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,prometheus
```

요청:

```bash
curl http://localhost:8080/actuator/prometheus
```

Prometheus는 이 endpoint를 주기적으로 수집한다.

## Grafana

Grafana는 메트릭을 시각화하는 도구다.

일반적인 조합:

```text
Spring Boot -> /actuator/prometheus -> Prometheus -> Grafana
```

Prometheus가 숫자를 모으고, Grafana가 대시보드로 보여준다.

대시보드에서 자주 보는 항목:

- 요청 수
- 평균 응답 시간
- p95, p99 응답 시간
- 오류율
- JVM 메모리
- GC 시간
- DB 커넥션 풀 사용량

## 커스텀 메트릭

업무 지표도 메트릭으로 남길 수 있다.

예를 들어 할 일 생성 횟수를 기록해 보자.

```java
package com.example.todo.todo;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.stereotype.Service;

@Service
public class TodoMetrics {

    private final Counter createdCounter;

    public TodoMetrics(MeterRegistry meterRegistry) {
        this.createdCounter = Counter.builder("todo.created")
                .description("Number of created todos")
                .register(meterRegistry);
    }

    public void incrementCreated() {
        createdCounter.increment();
    }
}
```

Service에서 사용:

```java
@Transactional
public TodoResponse create(TodoCreateRequest request) {
    Todo todo = todoRepository.save(new Todo(request.title()));
    todoMetrics.incrementCreated();
    return TodoResponse.from(todo);
}
```

확인:

```bash
curl http://localhost:8080/actuator/metrics/todo.created
```

## 태그 사용하기

메트릭에는 태그를 붙일 수 있다.

```java
Counter.builder("todo.created")
        .tag("source", "api")
        .register(meterRegistry);
```

태그는 필터링과 집계에 유용하다.

하지만 사용자 ID, 주문 ID처럼 값 종류가 너무 많은 태그는 피한다. 태그 값 종류가 폭발하면 메트릭 저장소에 큰 부담이 된다.

## 알림 기준

운영에서는 대시보드만 보는 것으로 부족하다. 기준을 넘으면 알림이 와야 한다.

예:

- 5xx 오류율이 5분 동안 3% 초과
- p95 응답 시간이 2초 초과
- DB active connection이 최대치에 근접
- JVM 메모리 사용량이 계속 증가
- health가 DOWN

좋은 알림은 바로 행동할 수 있어야 한다. 너무 많은 알림은 결국 무시된다.

## 자주 하는 실수

### 평균 응답 시간만 본다

평균은 느린 일부 요청을 숨길 수 있다. p95, p99 같은 percentile을 함께 본다.

### 태그에 사용자 ID를 넣는다

카디널리티가 너무 커져 메트릭 시스템이 힘들어진다.

### 메트릭만 보고 원인을 단정한다

메트릭은 증상을 보여준다. 원인 분석에는 로그와 트레이스가 함께 필요하다.
