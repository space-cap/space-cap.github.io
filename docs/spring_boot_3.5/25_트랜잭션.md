# 트랜잭션

## 이번 장에서 배울 것

이 장에서는 트랜잭션을 배운다.

트랜잭션은 DB 작업을 안전하게 묶는 단위다. Spring 애플리케이션에서 데이터가 꼬이지 않게 하려면 트랜잭션을 반드시 이해해야 한다.

## 트랜잭션이 필요한 이유

예를 들어 할 일 생성과 활동 로그 저장을 함께 한다고 하자.

1. 할 일을 저장한다.
2. 활동 로그를 저장한다.

첫 번째는 성공했는데 두 번째가 실패하면 어떻게 될까?

```text
할 일은 생겼지만 로그는 없다.
```

이 상태가 괜찮을 수도 있지만, 어떤 업무에서는 치명적이다. 두 작업이 반드시 함께 성공하거나 함께 실패해야 한다면 트랜잭션이 필요하다.

## ACID

트랜잭션의 대표 속성은 ACID다.

| 속성 | 의미 |
| --- | --- |
| Atomicity | 모두 성공하거나 모두 실패한다 |
| Consistency | 데이터 규칙을 깨지 않는다 |
| Isolation | 동시에 실행되는 트랜잭션끼리 서로 방해하지 않는다 |
| Durability | 커밋된 결과는 보존된다 |

처음에는 Atomicity, 즉 "한 묶음으로 성공하거나 실패한다"를 가장 먼저 기억하자.

## `@Transactional`

Spring에서는 `@Transactional`로 트랜잭션을 선언한다.

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class TodoService {

    private final TodoRepository todoRepository;

    public TodoService(TodoRepository todoRepository) {
        this.todoRepository = todoRepository;
    }

    @Transactional
    public TodoResponse create(TodoCreateRequest request) {
        Todo todo = new Todo(request.title());
        Todo saved = todoRepository.save(todo);
        return TodoResponse.from(saved);
    }
}
```

메서드가 정상 종료되면 커밋된다. 런타임 예외가 발생하면 기본적으로 롤백된다.

## 읽기 전용 트랜잭션

조회 메서드에는 `readOnly = true`를 붙인다.

```java
@Transactional(readOnly = true)
public TodoResponse findById(Long id) {
    Todo todo = todoRepository.findById(id)
            .orElseThrow(() -> new TodoNotFoundException(id));
    return TodoResponse.from(todo);
}
```

읽기 전용 트랜잭션은 이 메서드가 데이터를 변경하지 않는다는 의도를 드러낸다. JPA와 DB 연결 풀 수준에서 최적화에 도움이 될 수 있다.

## 변경 감지와 트랜잭션

JPA 변경 감지는 트랜잭션 안에서 의미가 있다.

```java
@Transactional
public TodoResponse complete(Long id) {
    Todo todo = todoRepository.findById(id)
            .orElseThrow(() -> new TodoNotFoundException(id));

    todo.complete();

    return TodoResponse.from(todo);
}
```

`todoRepository.save(todo)`를 다시 호출하지 않아도 트랜잭션이 끝날 때 JPA가 변경을 감지하고 update SQL을 실행한다.

하지만 트랜잭션 밖에서 Entity를 변경하면 기대한 대로 저장되지 않을 수 있다.

## 롤백 규칙

Spring의 기본 롤백 규칙은 다음과 같다.

- `RuntimeException`과 그 하위 예외: 롤백
- `Error`: 롤백
- 체크 예외: 기본적으로 롤백하지 않음

대부분의 비즈니스 예외는 `RuntimeException`을 상속해 만든다.

```java
public class TodoNotFoundException extends RuntimeException {

    public TodoNotFoundException(Long id) {
        super("할 일을 찾을 수 없습니다. id=" + id);
    }
}
```

체크 예외에도 롤백하고 싶으면 다음처럼 지정할 수 있다.

```java
@Transactional(rollbackFor = Exception.class)
public void doSomething() throws Exception {
}
```

## 클래스에 붙이기

Service 클래스 전체에 기본 트랜잭션을 줄 수 있다.

```java
@Service
@Transactional(readOnly = true)
public class TodoService {

    @Transactional
    public TodoResponse create(TodoCreateRequest request) {
        // 쓰기 작업
    }

    public TodoResponse findById(Long id) {
        // 읽기 작업
    }
}
```

클래스에는 읽기 전용을 기본으로 두고, 쓰기 메서드에만 `@Transactional`을 다시 붙이는 방식도 자주 사용한다.

## 트랜잭션은 Service에 두는 것이 좋다

트랜잭션은 보통 Service 계층에 둔다.

이유는 다음과 같다.

- 하나의 비즈니스 작업이 여러 Repository 호출을 포함할 수 있다.
- Controller는 HTTP 입구 역할에 집중해야 한다.
- Repository는 DB 접근에 집중해야 한다.

트랜잭션 경계는 비즈니스 작업 단위와 잘 맞아야 한다.

## self-invocation 문제

Spring의 선언적 트랜잭션은 프록시 기반으로 동작한다.

같은 클래스 안에서 `this.someTransactionalMethod()`처럼 내부 호출을 하면 트랜잭션이 기대대로 적용되지 않을 수 있다.

나쁜 예:

```java
public void outer() {
    this.inner();
}

@Transactional
public void inner() {
}
```

처음에는 한 Service 메서드 안에서 트랜잭션 경계를 명확히 잡는 방식으로 피하는 것이 좋다.

## 자주 하는 실수

### Controller에 트랜잭션을 붙인다

가능은 하지만 보통 Service에 붙이는 것이 구조상 좋다.

### 조회 메서드에 쓰기 트랜잭션을 사용한다

조회는 `@Transactional(readOnly = true)`를 사용한다.

### checked exception 롤백을 기대한다

체크 예외는 기본적으로 롤백되지 않는다. 필요하면 `rollbackFor`를 지정한다.

### private 메서드에 `@Transactional`을 붙인다

프록시 기반 트랜잭션은 일반적으로 외부에서 호출되는 public 메서드에 적용하는 것이 기본이다.
