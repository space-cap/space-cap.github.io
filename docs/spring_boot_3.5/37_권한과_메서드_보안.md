# 권한과 메서드 보안

## 이번 장에서 배울 것

이 장에서는 Spring Security의 권한 처리와 메서드 보안을 배운다.

보안은 로그인만으로 끝나지 않는다. 로그인한 사용자가 어떤 일을 할 수 있는지 판단해야 한다. 이것이 인가다.

## URL 기반 인가

가장 먼저 배우는 인가는 URL 기반 인가다.

```java
http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/").permitAll()
        .requestMatchers("/admin/**").hasRole("ADMIN")
        .requestMatchers("/api/todos/**").hasAnyRole("USER", "ADMIN")
        .anyRequest().authenticated()
);
```

의미:

- `/`는 누구나 접근 가능
- `/admin/**`은 ADMIN 역할 필요
- `/api/todos/**`는 USER 또는 ADMIN 역할 필요
- 그 외 요청은 로그인 필요

URL 기반 인가는 HTTP 경로 단위로 빠르게 접근을 제어할 수 있다.

## role과 authority

role은 보통 큰 역할을 표현한다.

```text
ROLE_USER
ROLE_ADMIN
```

authority는 더 세밀한 권한을 표현할 수 있다.

```text
todo:read
todo:write
user:delete
```

Spring Security에서:

```java
.roles("ADMIN")
```

은 내부적으로 `ROLE_ADMIN` authority를 만든다.

따라서:

```java
.hasRole("ADMIN")
```

은 `ROLE_ADMIN`을 검사한다.

직접 authority를 검사하려면:

```java
.hasAuthority("todo:write")
```

를 사용한다.

## 메서드 보안이 필요한 이유

URL 기반 인가만으로는 부족할 때가 있다.

예:

```text
모든 사용자가 /api/todos/{id}에 접근할 수는 있다.
하지만 본인의 Todo만 수정할 수 있어야 한다.
```

이런 규칙은 URL 패턴만으로 표현하기 어렵다. Service 메서드 수준에서 권한을 검사하는 것이 더 자연스럽다.

## 메서드 보안 활성화

메서드 보안을 사용하려면 `@EnableMethodSecurity`를 추가한다.

```java
package com.example.todo.security;

import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;

@Configuration
@EnableMethodSecurity
public class MethodSecurityConfig {
}
```

이제 `@PreAuthorize`, `@PostAuthorize` 같은 애너테이션을 사용할 수 있다.

## `@PreAuthorize`

메서드 실행 전에 권한을 검사한다.

```java
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.stereotype.Service;

@Service
public class AdminService {

    @PreAuthorize("hasRole('ADMIN')")
    public void deleteUser(Long userId) {
        // 관리자만 실행 가능
    }
}
```

ADMIN이 아닌 사용자가 호출하면 접근이 거부된다.

## 현재 사용자 이름 사용하기

SpEL 표현식에서 현재 인증 정보를 사용할 수 있다.

```java
@PreAuthorize("#username == authentication.name")
public UserProfileResponse findProfile(String username) {
    // 자기 프로필만 조회 가능
}
```

`authentication.name`은 현재 로그인 사용자의 이름이다.

## 본인 리소스 검사

실무에서는 다음과 같은 검사가 많다.

```text
이 Todo의 소유자가 현재 사용자와 같은가?
```

표현식이 복잡해지면 별도 보안 컴포넌트로 분리한다.

```java
package com.example.todo.security;

import org.springframework.stereotype.Component;

@Component
public class TodoPermissionEvaluator {

    private final TodoRepository todoRepository;

    public TodoPermissionEvaluator(TodoRepository todoRepository) {
        this.todoRepository = todoRepository;
    }

    public boolean isOwner(Long todoId, String username) {
        return todoRepository.findById(todoId)
                .map(todo -> todo.getOwnerUsername().equals(username))
                .orElse(false);
    }
}
```

Service:

```java
@PreAuthorize("@todoPermissionEvaluator.isOwner(#todoId, authentication.name)")
public TodoResponse update(Long todoId, TodoUpdateRequest request) {
    // 소유자만 수정 가능
}
```

표현식에서 `@beanName` 형태로 Spring Bean을 참조할 수 있다.

## `@PostAuthorize`

`@PostAuthorize`는 메서드 실행 후 결과를 보고 권한을 검사한다.

```java
@PostAuthorize("returnObject.username == authentication.name")
public UserProfileResponse findProfile(Long userId) {
    return userRepository.findProfile(userId);
}
```

결과 객체를 검사할 수 있다는 장점이 있지만, 이미 메서드가 실행된 뒤다. 데이터 조회 비용이나 부작용이 있는 작업에는 조심해서 사용한다.

## 도메인 규칙과 보안 규칙

보안 규칙과 도메인 규칙은 섞이기 쉽다.

보안 규칙:

```text
현재 사용자가 이 리소스에 접근할 수 있는가?
```

도메인 규칙:

```text
완료된 Todo를 다시 수정할 수 있는가?
```

둘 다 Service 근처에서 만날 수 있지만 성격이 다르다. 권한 검사는 Spring Security의 메서드 보안으로, 상태 전이 규칙은 도메인 객체나 Service 로직으로 표현하는 것이 좋다.

## 권한 이름 설계

간단한 애플리케이션:

```text
ROLE_USER
ROLE_ADMIN
```

조금 더 복잡한 API:

```text
todo:read
todo:write
todo:delete
user:read
user:manage
```

권한 이름은 API와 운영 정책에 오래 남는다. 처음에는 단순하게 시작하고, 필요할 때 세분화한다.

## 자주 하는 실수

### `hasRole("ROLE_ADMIN")`처럼 쓴다

`hasRole("ADMIN")`으로 쓴다. `ROLE_` 접두사는 Spring Security가 내부적으로 붙여 검사한다.

### 메서드 보안을 활성화하지 않는다

`@PreAuthorize`를 붙였는데 동작하지 않으면 `@EnableMethodSecurity`가 있는지 확인한다.

### Controller에만 권한 검사를 둔다

중요한 비즈니스 권한은 Service 메서드에서도 보호하는 것이 좋다. Controller가 아닌 다른 경로로 Service가 호출될 수 있기 때문이다.
