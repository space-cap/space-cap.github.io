# 운영에서 자주 나는 문제

## 이번 장에서 배울 것

이 장에서는 Spring Boot 운영 중 자주 만나는 문제와 진단 방법을 정리한다.

운영 장애는 대개 갑자기 찾아온다. 이때 중요한 것은 당황하지 않고 증거를 모으는 순서다. 로그, 메트릭, health, 설정, 최근 변경 사항을 차례로 확인한다.

## 먼저 확인할 것

장애가 발생하면 다음 순서로 확인한다.

1. 애플리케이션이 살아 있는가
2. 어떤 에러 로그가 있는가
3. 최근 배포나 설정 변경이 있었는가
4. DB, Redis, 외부 API 연결은 정상인가
5. CPU, 메모리, 스레드, 커넥션 풀은 정상인가
6. 특정 endpoint만 문제인가, 전체가 문제인가
7. 트래픽이 평소보다 늘었는가

느낌보다 증거를 먼저 본다.

## 포트 충돌

증상:

```text
Port 8080 was already in use
```

원인:

- 이미 같은 포트로 다른 애플리케이션 실행 중
- 이전 프로세스가 종료되지 않음
- 로컬 DB나 프록시가 같은 포트 사용

해결:

```yaml
server:
  port: 8081
```

또는 기존 프로세스를 종료한다.

운영에서는 포트 충돌이 배포 스크립트나 프로세스 관리 설정 문제일 수 있다.

## DB 연결 실패

증상:

```text
Connection refused
Unable to obtain JDBC Connection
Communications link failure
```

확인할 것:

- DB 호스트와 포트
- 사용자 이름과 비밀번호
- DB가 실행 중인지
- 방화벽과 보안 그룹
- 커넥션 풀 설정
- DB 최대 연결 수

Spring Boot 설정:

```yaml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
```

Actuator health에서 DB 상태가 DOWN으로 보일 수도 있다.

```bash
curl http://localhost:8080/actuator/health
```

## Bean 충돌

증상:

```text
No qualifying bean of type ...
expected single matching bean but found 2
```

원인:

- 같은 타입의 Bean이 여러 개 있음
- 필요한 Bean이 등록되지 않음
- 컴포넌트 스캔 범위 밖에 클래스가 있음
- Profile 조건 때문에 Bean이 빠짐

해결 방향:

- `@Primary` 사용
- `@Qualifier` 사용
- Bean 이름 확인
- Profile 확인
- 패키지 위치 확인

Actuator의 `/actuator/beans`와 `/actuator/conditions`가 원인 분석에 도움이 된다. 운영에서 노출할 때는 보안에 주의한다.

## 메모리 문제

증상:

```text
java.lang.OutOfMemoryError
```

확인할 것:

- JVM heap 크기
- 트래픽 증가
- 대용량 파일 처리
- 캐시가 무한히 커지는지
- 컬렉션에 데이터를 계속 쌓는지
- DB 조회가 너무 많은 데이터를 한 번에 가져오는지

Actuator 메트릭:

```text
jvm.memory.used
jvm.memory.max
jvm.gc.pause
```

운영에서는 heap dump 분석이 필요할 수 있다. 단, heap dump에는 민감 정보가 포함될 수 있으므로 관리에 주의한다.

## 응답 지연

증상:

- API 응답 시간이 길어짐
- 타임아웃 증가
- p95, p99 응답 시간 상승

확인할 것:

- DB 쿼리 지연
- 외부 API 지연
- 커넥션 풀 고갈
- 스레드 풀 고갈
- GC pause 증가
- 특정 endpoint만 느린지

메트릭:

```text
http.server.requests
hikaricp.connections.active
jvm.gc.pause
```

트레이스가 있다면 느린 span을 확인한다.

## 500 오류 증가

증상:

- 5xx 오류율 증가
- 사용자 요청 실패

확인할 것:

- 최근 배포
- 예외 로그
- 특정 요청 값에서만 발생하는지
- DB migration 누락
- 외부 API 응답 변경
- 설정 누락

로그에서 `Caused by` 근처를 본다. 가장 아래 줄만 보면 원인을 놓칠 수 있다.

## 로그 레벨 조정

운영 중 특정 패키지 로그를 잠시 자세히 보고 싶을 수 있다.

Actuator loggers endpoint를 노출하고 권한을 제한하면 로그 레벨을 확인하거나 바꿀 수 있다.

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,loggers
```

요청:

```bash
curl http://localhost:8080/actuator/loggers/com.example.todo
```

운영에서 동적으로 로그 레벨을 바꿀 때는 반드시 되돌리는 절차를 함께 둔다.

## 설정 누락

증상:

```text
Could not resolve placeholder
```

또는 애플리케이션 시작 실패.

원인:

- 환경 변수가 없음
- Profile이 잘못 활성화됨
- Secret 이름이 틀림
- 배포 환경 설정 누락

해결:

- 활성 Profile 확인
- 환경 변수 확인
- 설정 이름 확인
- `@ConfigurationProperties` 검증 도입

운영에서는 필수 설정이 없으면 시작 실패하는 편이 낫다.

## 장애 대응 기록

장애가 끝나면 반드시 기록한다.

기록할 것:

- 언제 발생했는가
- 영향 범위는 무엇인가
- 원인은 무엇인가
- 어떻게 탐지했는가
- 어떻게 복구했는가
- 다시 막기 위해 무엇을 바꿀 것인가

운영 실력은 장애를 한 번도 안 내는 데서만 나오지 않는다. 같은 장애를 반복하지 않게 만드는 데서 커진다.

## 자주 하는 실수

### 로그만 보고 메트릭을 보지 않는다

로그는 사건을 보여주고 메트릭은 흐름을 보여준다. 함께 봐야 한다.

### 최근 변경 사항을 확인하지 않는다

장애의 많은 원인은 최근 배포나 설정 변경과 관련이 있다.

### 운영 endpoint를 무분별하게 연다

진단용 endpoint는 강력하지만 민감하다. 접근 제어를 반드시 고려한다.

## 확인 문제

1. 운영 장애가 발생했을 때 가장 먼저 확인할 항목은 무엇인가?
2. DB 연결 실패 시 확인해야 할 설정은 무엇인가?
3. 응답 지연을 분석할 때 도움이 되는 메트릭은 무엇인가?
4. 장애 대응 후 기록해야 할 내용에는 무엇이 있는가?
