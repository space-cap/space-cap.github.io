# DB 마이그레이션 Flyway와 Liquibase

## 이번 장에서 배울 것

이 장에서는 DB 마이그레이션 도구를 배운다.

애플리케이션 코드는 Git으로 변경 이력을 관리한다. DB 스키마도 마찬가지다. 테이블 생성, 컬럼 추가, 인덱스 추가 같은 변경을 기록하고 순서대로 적용해야 한다.

Flyway와 Liquibase는 이 일을 도와주는 대표 도구다.

## 왜 마이그레이션 도구가 필요할까?

초기 학습에서는 `ddl-auto: create-drop`이나 `schema.sql`로 충분하다.

하지만 실무에서는 문제가 생긴다.

- 운영 DB를 매번 삭제하고 다시 만들 수 없다.
- 여러 개발자가 스키마를 동시에 바꾼다.
- 어떤 변경이 언제 반영됐는지 알아야 한다.
- 운영, 개발, 테스트 DB의 스키마가 같아야 한다.
- 배포 시 누락된 DB 변경을 자동으로 적용하고 싶다.

마이그레이션 도구는 DB 변경 이력을 파일로 관리하고, 아직 적용되지 않은 변경만 순서대로 실행한다.

## Flyway와 Liquibase 비교

| 구분 | Flyway | Liquibase |
| --- | --- | --- |
| 기본 방식 | SQL 파일 중심 | XML, YAML, JSON, SQL 등 |
| 학습 난이도 | 비교적 단순 | 기능이 풍부한 만큼 복잡 |
| 장점 | 직관적, SQL 그대로 관리 | 변경 세트 관리 기능 풍부 |
| 추천 시작점 | 초보자와 SQL 중심 팀 | 복잡한 변경 추적이 필요한 팀 |

처음에는 Flyway로 시작하는 것을 추천한다. SQL 파일만으로 흐름을 이해하기 쉽다.

## Flyway 의존성

H2에서 Flyway를 사용하려면:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
    implementation 'org.flywaydb:flyway-core'
    runtimeOnly 'com.h2database:h2'
}
```

PostgreSQL에서는 DB별 모듈도 추가한다.

```groovy
dependencies {
    implementation 'org.flywaydb:flyway-core'
    implementation 'org.flywaydb:flyway-database-postgresql'
    runtimeOnly 'org.postgresql:postgresql'
}
```

Spring Boot는 Flyway가 클래스패스에 있으면 시작 시 마이그레이션을 자동 실행한다.

## Flyway 파일 위치와 이름

기본 위치:

```text
src/main/resources/db/migration
```

파일 이름 규칙:

```text
V버전__설명.sql
```

예:

```text
V1__create_todos_table.sql
V2__add_due_date_to_todos.sql
V3__create_users_table.sql
```

버전과 설명 사이에는 밑줄 두 개 `__`를 사용한다.

## 첫 Flyway 마이그레이션

`src/main/resources/db/migration/V1__create_todos_table.sql`:

```sql
create table todos (
    id bigint generated by default as identity primary key,
    title varchar(100) not null,
    completed boolean not null default false,
    created_at timestamp not null
);
```

`application.yml`:

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

이제 Hibernate가 테이블을 만들지 않고, Flyway가 만든 스키마와 Entity 매핑이 맞는지 검증한다.

## Flyway 이력 테이블

Flyway는 DB에 이력 테이블을 만든다.

보통 이름은 다음과 같다.

```text
flyway_schema_history
```

이 테이블에는 어떤 마이그레이션 파일이 언제 적용됐는지 기록된다.

이미 적용된 파일은 다시 실행하지 않는다. 그래서 한번 적용된 마이그레이션 파일은 함부로 수정하지 않는 것이 원칙이다.

## 마이그레이션 파일 수정 원칙

아직 팀원이나 운영 DB에 적용되지 않은 파일은 수정할 수 있다.

하지만 이미 공유되거나 운영에 적용된 파일은 수정하지 않는다. 대신 새 버전 파일을 만든다.

나쁜 예:

```text
V1__create_todos_table.sql 파일을 운영 반영 후 수정
```

좋은 예:

```text
V2__add_todos_due_date.sql 새로 추가
```

## Liquibase 의존성

Liquibase를 사용하려면:

```groovy
dependencies {
    implementation 'org.liquibase:liquibase-core'
}
```

Spring Boot는 Liquibase가 클래스패스에 있으면 자동으로 실행할 수 있다.

대표 설정:

```yaml
spring:
  liquibase:
    change-log: classpath:db/changelog/db.changelog-master.yaml
```

## Liquibase 예제

`src/main/resources/db/changelog/db.changelog-master.yaml`:

```yaml
databaseChangeLog:
  - changeSet:
      id: 1
      author: spring-boot-study
      changes:
        - createTable:
            tableName: todos
            columns:
              - column:
                  name: id
                  type: bigint
                  autoIncrement: true
                  constraints:
                    primaryKey: true
                    nullable: false
              - column:
                  name: title
                  type: varchar(100)
                  constraints:
                    nullable: false
              - column:
                  name: completed
                  type: boolean
                  defaultValueBoolean: false
                  constraints:
                    nullable: false
              - column:
                  name: created_at
                  type: timestamp
                  constraints:
                    nullable: false
```

Liquibase는 SQL보다 장황하지만 DB 독립적인 변경 표현과 다양한 관리 기능이 장점이다.

## Flyway와 schema.sql을 같이 써도 될까?

Spring Boot 공식 문서는 Flyway나 Liquibase 같은 상위 마이그레이션 도구를 사용한다면 `schema.sql`, `data.sql` 방식과 섞어 쓰는 것을 권장하지 않는다.

초보 단계에서는 다음 기준이 좋다.

- 학습 초반: `schema.sql`, `data.sql`
- JPA 학습 초반: `ddl-auto: create-drop`
- 실무형 구조: Flyway 또는 Liquibase

한 프로젝트에서 스키마 생성 책임을 여러 도구가 나눠 가지면 예측하기 어려워진다.

## 자주 하는 실수

### 이미 적용된 Flyway 파일을 수정한다

Flyway는 체크섬으로 파일 변경을 감지한다. 이미 적용된 파일을 수정하면 오류가 날 수 있다.

### `ddl-auto: update`와 Flyway를 함께 무심코 쓴다

스키마 변경 주체가 둘이 되면 위험하다. Flyway를 쓴다면 JPA는 보통 `validate` 또는 `none`으로 둔다.

### 파일 이름의 밑줄을 하나만 쓴다

Flyway 파일은 `V1__create_table.sql`처럼 버전과 설명 사이에 밑줄 두 개를 사용한다.
