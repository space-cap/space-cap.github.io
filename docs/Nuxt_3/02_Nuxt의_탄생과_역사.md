# Nuxt의 탄생과 역사

## 이번 장에서 배울 것

- Nuxt가 왜 만들어졌는지
- Nuxt 1, Nuxt 2, Nuxt 3의 큰 흐름
- Nuxt 3에서 중요해진 변화

## Nuxt가 등장한 배경

Vue는 배우기 쉽고 화면을 만들기 편한 도구로 많은 사랑을 받았다. 하지만 Vue만으로 실제 서비스를 만들려면 개발자가 여러 결정을 직접 해야 했다.

- 라우터는 어떻게 설정할까?
- 서버 사이드 렌더링은 어떻게 붙일까?
- 페이지별 코드는 어떻게 나눌까?
- SEO는 어떻게 처리할까?
- 빌드와 배포는 어떤 방식으로 할까?

이 문제를 매번 프로젝트마다 다시 해결하는 것은 번거롭다. Nuxt는 이런 반복을 줄이기 위해 만들어졌다. Vue로 서비스를 만들 때 자주 필요한 구조를 미리 준비해 둔 프레임워크라고 볼 수 있다.

## Nuxt 1

Nuxt 1은 Vue 애플리케이션에서 서버 사이드 렌더링을 쉽게 사용할 수 있도록 도와주는 도구로 출발했다.

당시에는 SPA 방식의 프론트엔드 앱이 많이 사용되었다. SPA는 화면 전환이 부드럽다는 장점이 있지만, 검색 엔진 최적화와 초기 로딩 속도에서 불리할 수 있었다.

Nuxt는 Vue 컴포넌트를 서버에서 먼저 HTML로 렌더링하고, 브라우저에서 다시 Vue 앱으로 연결하는 흐름을 제공했다. 이 덕분에 Vue로도 SEO에 강한 웹사이트를 만들기 쉬워졌다.

## Nuxt 2

Nuxt 2는 Nuxt를 더 안정적인 프레임워크로 성장시킨 버전이다. Vue 2 생태계와 함께 널리 사용되었고, 많은 실무 프로젝트에서 선택되었다.

Nuxt 2에서는 다음과 같은 흐름이 익숙했다.

- `pages` 폴더를 이용한 파일 기반 라우팅
- `layouts` 폴더를 이용한 공통 화면 구조
- `asyncData`, `fetch`를 이용한 데이터 가져오기
- 플러그인과 모듈을 이용한 기능 확장
- 정적 사이트 생성

Nuxt 2는 Vue 기반 SSR 프레임워크의 대표적인 선택지 중 하나가 되었다.

## Nuxt 3

Nuxt 3는 Vue 3 시대에 맞춰 내부 구조가 크게 바뀐 버전이다. 단순히 문법만 바뀐 것이 아니라, 서버 엔진과 빌드 도구, 타입 지원, 렌더링 전략까지 전반적으로 새로워졌다.

Nuxt 3의 중요한 변화는 다음과 같다.

- Vue 3와 Composition API 기반
- Vite 기반의 빠른 개발 경험
- Nitro 서버 엔진 도입
- TypeScript 친화적인 구조
- `useFetch`, `useAsyncData` 같은 새로운 데이터 가져오기 방식
- 서버 라우트와 API 기능 강화
- 하이브리드 렌더링 지원

Nuxt 3에서는 프론트엔드 앱뿐 아니라 서버 API까지 같은 프로젝트 안에서 만들 수 있다. 그래서 작은 서비스나 프로토타입을 만들 때도 강력하고, 배포 대상도 유연하다.

## Nuxt 3를 배울 때 중요한 관점

Nuxt 3를 공부할 때는 단순히 "Vue에 기능이 추가된 것"으로만 보면 어렵다. Nuxt는 Vue 앱을 실제 서비스로 만들기 위한 규칙과 흐름을 제공한다.

특히 다음 질문을 계속 떠올리면 좋다.

- 이 코드는 서버에서 실행될까, 브라우저에서 실행될까?
- 이 페이지는 매 요청마다 렌더링해야 할까, 미리 만들어 두어도 될까?
- 이 데이터는 사용자마다 다른가, 모두에게 같은가?
- 이 설정은 빌드할 때 정해지는가, 실행 중에 바뀔 수 있는가?

이 질문들이 Nuxt의 핵심 개념으로 이어진다.

## 정리

Nuxt는 Vue 애플리케이션의 라우팅, 렌더링, SEO, 빌드, 배포 문제를 더 쉽게 해결하기 위해 등장했다.

Nuxt 1과 Nuxt 2가 Vue 기반 SSR 프레임워크의 기반을 다졌다면, Nuxt 3는 Vue 3, Vite, Nitro, TypeScript 친화 구조를 바탕으로 더 넓은 애플리케이션 개발 경험을 제공한다.
