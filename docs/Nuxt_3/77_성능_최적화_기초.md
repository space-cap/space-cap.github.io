# 성능 최적화 기초

## 이번 장에서 배울 것

- 성능 최적화가 필요한 이유
- Nuxt에서 성능에 영향을 주는 요소
- 이미지, JavaScript, 데이터 요청 최적화
- 초보자가 먼저 챙길 체크리스트

## 성능 최적화란

성능 최적화는 사용자가 더 빠르고 부드럽게 웹사이트를 사용할 수 있도록 만드는 작업이다.

성능이 나쁘면 다음 문제가 생긴다.

- 첫 화면이 늦게 보인다.
- 버튼 클릭 후 반응이 느리다.
- 페이지 이동이 답답하다.
- 모바일에서 데이터 사용량이 커진다.
- 검색 엔진 평가에 불리할 수 있다.

Nuxt는 SSR, SSG, 코드 분할, 이미지 최적화 같은 도구를 제공하지만, 개발자가 구조를 잘못 잡으면 여전히 느려질 수 있다.

## 성능에 영향을 주는 요소

Nuxt 앱의 성능에는 여러 요소가 영향을 준다.

- 렌더링 방식
- JavaScript 번들 크기
- 이미지 용량
- 데이터 요청 횟수
- API 응답 시간
- 폰트 로딩
- hydration 비용
- 불필요한 컴포넌트 렌더링

처음에는 모든 것을 한 번에 최적화하려고 하지 말고, 가장 큰 병목부터 찾는 것이 좋다.

## 이미지 최적화

이미지는 성능에 큰 영향을 준다.

다음 습관을 지키자.

- 화면에 필요한 크기보다 너무 큰 이미지를 쓰지 않는다.
- 의미 있는 이미지에는 `alt`를 작성한다.
- 첫 화면 밖의 이미지는 lazy loading을 고려한다.
- Nuxt Image의 `<NuxtImg>`를 활용한다.
- `width`와 `height`를 지정해 레이아웃 흔들림을 줄인다.

예시:

```vue
<template>
  <NuxtImg
    src="/images/post-cover.png"
    width="800"
    height="420"
    alt="게시글 대표 이미지"
    loading="lazy"
  />
</template>
```

첫 화면 핵심 이미지는 lazy loading을 피하는 것이 좋다. 중요한 이미지는 빨리 보여야 하기 때문이다.

## JavaScript 줄이기

Nuxt 앱은 페이지별로 코드를 나누어 로드할 수 있다.

하지만 무거운 라이브러리를 많이 설치하면 초기 JavaScript가 커질 수 있다.

다음 기준을 생각하자.

- 정말 필요한 라이브러리인가?
- 일부 기능만 직접 구현해도 되는가?
- 클라이언트에서만 필요한 라이브러리인가?
- lazy import가 가능한가?
- UI 라이브러리를 과하게 섞고 있지 않은가?

큰 차트 라이브러리나 에디터 같은 도구는 필요할 때만 로드하는 전략을 고려한다.

## Lazy 컴포넌트

Nuxt에서는 컴포넌트 이름 앞에 `Lazy`를 붙여 지연 로딩할 수 있다.

```vue
<template>
  <LazyHeavyChart />
</template>
```

처음 화면에 꼭 필요하지 않은 무거운 컴포넌트에 사용할 수 있다.

단, 사용자가 바로 봐야 하는 핵심 UI까지 무리하게 lazy로 만들면 오히려 사용자 경험이 나빠질 수 있다.

## 데이터 요청 줄이기

같은 데이터를 여러 컴포넌트에서 중복 요청하면 성능이 나빠진다.

Nuxt에서는 다음 도구를 활용한다.

- `useFetch`
- `useAsyncData`
- `useNuxtData`
- `refreshNuxtData`
- Pinia store
- 서버 API에서 여러 데이터를 한 번에 조합

홈 화면에서 게시글, 공지사항, 배너를 각각 따로 요청할 수도 있지만, 필요하면 서버 API 하나에서 조합해 내려줄 수도 있다.

## 캐시 전략

모든 데이터를 매번 새로 가져올 필요는 없다.

예를 들어 다음 데이터는 캐시하기 좋다.

- 블로그 글
- 문서 페이지
- 카테고리 목록
- 공개 상품 목록
- 변경이 적은 설정값

Nuxt에서는 `routeRules`로 route별 캐시나 렌더링 전략을 지정할 수 있다.

```ts
export default defineNuxtConfig({
  routeRules: {
    '/blog/**': {
      isr: 3600
    }
  }
})
```

이 예시는 블로그 페이지를 일정 시간 캐시하는 전략으로 이해할 수 있다. 실제 동작은 배포 플랫폼과 Nitro preset에 따라 달라질 수 있다.

## 폰트 최적화

폰트도 성능에 영향을 준다.

다음 습관을 지키자.

- 필요한 굵기만 사용한다.
- `woff2` 형식을 우선 사용한다.
- `font-display: swap`을 고려한다.
- 외부 폰트 요청을 너무 많이 만들지 않는다.
- Nuxt Fonts 모듈을 검토한다.

폰트가 늦게 로드되면 텍스트가 늦게 보이거나 화면이 흔들릴 수 있다.

## 측정 도구

성능은 감으로만 판단하면 안 된다.

다음 도구를 사용할 수 있다.

- Chrome DevTools Lighthouse
- Chrome DevTools Performance
- Network 탭
- WebPageTest
- PageSpeed Insights
- 배포 플랫폼의 분석 도구

처음에는 Lighthouse와 Network 탭만 잘 봐도 많은 문제를 찾을 수 있다.

## 초보자 체크리스트

- 이미지 크기가 적절한가?
- 첫 화면 밖 이미지는 lazy loading을 적용했는가?
- 너무 무거운 라이브러리를 설치하지 않았는가?
- 같은 API를 중복 요청하지 않는가?
- 페이지 성격에 맞는 렌더링 전략을 선택했는가?
- 빌드 결과를 `npm run preview`로 확인했는가?
- Lighthouse로 기본 성능을 확인했는가?

## 정리

Nuxt 성능 최적화는 이미지, JavaScript, 데이터 요청, 캐시, 렌더링 전략을 함께 보는 일이다. 처음에는 큰 병목부터 찾고, 측정 도구로 개선 효과를 확인하는 습관이 중요하다.
