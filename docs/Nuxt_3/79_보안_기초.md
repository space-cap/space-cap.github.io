# 보안 기초

## 이번 장에서 배울 것

- Nuxt 앱에서 자주 만나는 보안 위험
- XSS, CSRF, 비밀 키 노출의 기본
- 서버 API 검증의 중요성
- 보안 헤더와 nuxt-security 모듈

## 보안은 나중 일이 아니다

초보자는 보안을 배포 직전에 생각하기 쉽다.

하지만 보안은 구조를 만들 때부터 함께 생각해야 한다.

특히 Nuxt는 프론트엔드와 서버 API를 같은 프로젝트에서 다룰 수 있기 때문에, 클라이언트와 서버의 경계를 명확히 이해해야 한다.

## 클라이언트는 믿지 않는다

브라우저에서 실행되는 코드는 사용자가 볼 수 있고 조작할 수 있다.

따라서 다음을 클라이언트에서만 처리하면 안 된다.

- 관리자 권한 확인
- 결제 금액 검증
- 게시글 삭제 권한
- 비밀 API 키 보호
- 입력값 최종 검증

UI에서 버튼을 숨기는 것은 사용자 경험을 위한 것이지 보안이 아니다.

중요한 검증은 서버 API에서 다시 해야 한다.

## XSS

XSS는 Cross-Site Scripting의 줄임말이다.

사용자가 입력한 악성 스크립트가 다른 사용자 브라우저에서 실행되는 공격이다.

Vue 템플릿의 `{{ }}` 보간은 기본적으로 HTML을 escape한다.

```vue
<p>{{ userInput }}</p>
```

하지만 `v-html`은 HTML을 그대로 렌더링하므로 위험할 수 있다.

```vue
<div v-html="userInput" />
```

신뢰할 수 없는 사용자 입력을 `v-html`로 렌더링하지 않는다.

## useHead와 XSS

head 영역에 사용자 입력을 넣을 때도 주의해야 한다.

Nuxt는 안전한 head 관리를 돕지만, 신뢰할 수 없는 입력을 다룰 때는 `useHeadSafe`를 고려한다.

```vue
<script setup>
useHeadSafe({
  title: userTitle
})
</script>
```

사용자 입력을 script나 innerHTML로 넣는 구조는 피하는 것이 좋다.

## CSRF

CSRF는 Cross-Site Request Forgery의 줄임말이다.

사용자가 로그인된 상태를 악용해, 공격자가 원하지 않는 요청을 보내게 만드는 공격이다.

쿠키 기반 인증을 사용할 때는 CSRF를 고려해야 한다.

완화 방법은 다음과 같다.

- `sameSite` 쿠키 설정
- CSRF token 사용
- 중요한 요청의 Origin 또는 Referer 확인
- GET 요청으로 상태를 변경하지 않기
- 서버에서 권한 재검증

로그인 세션 쿠키를 사용할 때는 `sameSite`, `httpOnly`, `secure` 옵션을 신중하게 설정한다.

## 비밀 키 노출

Nuxt에서 가장 흔한 실수 중 하나는 비밀 값을 클라이언트에 노출하는 것이다.

다음 값은 `runtimeConfig.public`에 넣으면 안 된다.

- DB 비밀번호
- 외부 API secret key
- 관리자 토큰
- 결제 secret key
- private access token

```ts
export default defineNuxtConfig({
  runtimeConfig: {
    apiSecret: '',
    public: {
      apiBase: ''
    }
  }
})
```

`public` 밖의 값은 서버 전용으로 다루고, 브라우저에서 필요한 값만 `public`에 둔다.

## 입력값 검증

서버 API는 사용자가 보낸 값을 반드시 검증해야 한다.

```ts
export default defineEventHandler(async (event) => {
  const body = await readBody(event)

  if (!body.title) {
    throw createError({
      statusCode: 400,
      statusMessage: '제목은 필수입니다.'
    })
  }

  return {
    ok: true
  }
})
```

TypeScript 타입은 실행 중 검증이 아니다. 서버에는 실제 값 검증이 필요하다.

## 보안 헤더

보안 헤더는 브라우저에게 보안 관련 정책을 알려 주는 HTTP header다.

대표적인 헤더는 다음과 같다.

- Content-Security-Policy
- X-Frame-Options
- Referrer-Policy
- Permissions-Policy
- Strict-Transport-Security

직접 설정할 수도 있지만, 실무에서는 검증된 모듈을 사용하는 것도 좋은 선택이다.

## nuxt-security 모듈

Nuxt 생태계에는 `nuxt-security` 모듈이 있다.

이 모듈은 OWASP 보안 패턴과 Helmet 기반 보안 헤더, 요청 제한, XSS 검증, CORS 설정 등을 도와준다.

설치 예시:

```bash
npx nuxi@latest module add security
```

`nuxt.config.ts`

```ts
export default defineNuxtConfig({
  modules: ['nuxt-security']
})
```

프로젝트에 도입할 때는 공식 문서를 보고 CSP, CORS, CSRF 옵션을 서비스에 맞게 조정해야 한다.

## 자주 하는 실수

가장 흔한 실수는 "프론트엔드에서 막았으니 안전하다"고 생각하는 것이다.

브라우저는 사용자가 조작할 수 있다. 실제 보안은 서버 검증에서 완성된다.

또 `.env`에 넣은 값을 모두 안전하다고 생각하는 것도 위험하다. `NUXT_PUBLIC_` 접두사가 붙은 값은 클라이언트에 노출될 수 있다.

## 정리

Nuxt 보안의 기본은 클라이언트와 서버의 경계를 이해하는 것이다. 클라이언트는 믿지 않고, 서버에서 입력과 권한을 검증하며, 비밀 값은 public에 노출하지 않는다. XSS, CSRF, 보안 헤더도 함께 고려해야 한다.
