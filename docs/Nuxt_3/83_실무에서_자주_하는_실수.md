# 실무에서 자주 하는 실수

## 이번 장에서 배울 것

- Nuxt 실무에서 자주 만나는 실수
- hydration mismatch의 원인
- 환경 변수와 보안 실수
- 렌더링 전략과 데이터 요청 실수

## 실수는 패턴이 있다

Nuxt를 처음 실무에 적용하면 비슷한 실수를 반복하기 쉽다.

대부분은 Nuxt가 서버와 클라이언트 양쪽에서 실행된다는 점을 놓쳐서 생긴다.

이번 장에서는 자주 만나는 실수를 미리 정리한다.

## window is not defined

가장 흔한 오류 중 하나다.

```ts
const width = window.innerWidth
```

Nuxt는 서버에서 코드를 실행할 수 있다. 서버에는 `window`가 없다.

브라우저 전용 코드는 클라이언트에서만 실행되도록 처리한다.

```vue
<script setup>
const width = ref(0)

onMounted(() => {
  width.value = window.innerWidth
})
</script>
```

plugin이라면 `.client.ts` 파일을 사용한다.

```txt
plugins/browser.client.ts
```

## hydration mismatch

hydration mismatch는 서버가 만든 HTML과 브라우저에서 처음 렌더링한 결과가 다를 때 발생한다.

예를 들어 서버와 클라이언트에서 다른 값을 렌더링하면 문제가 생긴다.

```vue
<template>
  <p>{{ Math.random() }}</p>
</template>
```

서버에서 만든 랜덤 값과 클라이언트에서 만든 랜덤 값이 다르기 때문이다.

해결 방법은 서버와 클라이언트의 첫 렌더링 결과를 같게 만드는 것이다.

클라이언트에서만 보여야 하는 값은 `onMounted` 이후에 표시하거나 `<ClientOnly>`를 사용한다.

```vue
<template>
  <ClientOnly>
    <p>브라우저에서만 표시</p>
  </ClientOnly>
</template>
```

## localStorage 바로 사용하기

`localStorage`도 브라우저에만 있다.

```ts
const token = localStorage.getItem('token')
```

SSR 중에는 오류가 날 수 있다.

```ts
const token = ref<string | null>(null)

onMounted(() => {
  token.value = localStorage.getItem('token')
})
```

인증 토큰을 localStorage에 저장하는 것은 보안상 위험할 수 있다. 인증 파트에서 다룬 것처럼 httpOnly 쿠키 기반 세션도 검토해야 한다.

## public runtimeConfig에 secret 넣기

비밀 값을 `runtimeConfig.public`에 넣는 실수는 매우 위험하다.

```ts
export default defineNuxtConfig({
  runtimeConfig: {
    public: {
      apiSecret: 'secret'
    }
  }
})
```

`public` 안의 값은 브라우저에 노출될 수 있다.

비밀 값은 public 밖에 둔다.

```ts
export default defineNuxtConfig({
  runtimeConfig: {
    apiSecret: '',
    public: {
      apiBase: ''
    }
  }
})
```

## 서버 API를 GitHub Pages에 배포하려는 실수

GitHub Pages는 정적 사이트만 지원한다.

`server/api`를 사용하는 Nuxt 앱은 GitHub Pages에서 서버 API를 실행할 수 없다.

서버 기능이 필요하면 Vercel, Netlify, Node 서버 같은 환경을 선택해야 한다.

정적 사이트만 필요하다면 `github_pages` preset과 `NUXT_APP_BASE_URL`을 설정해 배포한다.

## useFetch 중복 요청

여러 컴포넌트에서 같은 API를 각각 호출하면 중복 요청이 생길 수 있다.

공통 데이터는 상위 페이지에서 가져와 props로 내려주거나, Pinia/store, `useNuxtData`, API 레이어를 활용한다.

또 페이지 초기 데이터에는 단순 `$fetch`보다 `useFetch`나 `useAsyncData`를 우선 고려한다.

## GET 요청으로 데이터 변경하기

GET 요청은 데이터를 조회하는 용도다.

다음처럼 GET 요청으로 삭제를 처리하면 안 된다.

```txt
GET /api/posts/delete?id=1
```

삭제는 DELETE를 사용한다.

```txt
DELETE /api/posts/1
```

HTTP 메서드를 올바르게 쓰면 캐시, 보안, API 설계가 더 명확해진다.

## 서버 검증 누락

클라이언트에서 폼 검증을 했다고 서버 검증을 생략하면 안 된다.

브라우저 요청은 사용자가 조작할 수 있다.

서버 API에서는 다시 입력값을 검증해야 한다.

```ts
if (!body.title) {
  throw createError({
    statusCode: 400,
    statusMessage: '제목은 필수입니다.'
  })
}
```

## 너무 이른 추상화

한 번만 쓰는 컴포넌트나 API wrapper를 너무 빨리 공통화하면 오히려 복잡해진다.

좋은 기준은 반복이다.

- 같은 코드가 두세 번 반복된다.
- 변경 이유가 같다.
- 이름을 붙였을 때 역할이 분명하다.

이 조건이 보이면 추상화를 고려한다.

## 너무 많은 모듈 설치

Nuxt 모듈은 편리하지만 많이 설치할수록 관리할 것이 늘어난다.

다음 질문을 먼저 해 보자.

- 지금 정말 필요한가?
- Nuxt 3와 호환되는가?
- SSR에서 문제가 없는가?
- 유지보수되고 있는가?
- 더 단순한 방법은 없는가?

## 체크리스트

- 브라우저 전용 API를 서버에서 사용하지 않는가?
- 첫 렌더링 결과가 서버와 클라이언트에서 같은가?
- 비밀 값이 `public`에 들어가지 않았는가?
- 서버 API에서도 권한과 입력값을 검증하는가?
- 배포 플랫폼이 서버 기능을 지원하는가?
- 페이지 성격에 맞는 렌더링 전략을 선택했는가?
- 중복 API 요청이 많지 않은가?
- 모듈을 필요한 만큼만 설치했는가?

## 정리

Nuxt 실무 실수의 핵심은 서버와 클라이언트 경계를 놓치는 데서 많이 나온다. 브라우저 전용 API, hydration mismatch, 환경 변수 노출, 서버 검증 누락, 잘못된 배포 환경 선택을 특히 주의해야 한다.
