# 실무 폴더 구조

## 이번 장에서 배울 것

- Nuxt 기본 폴더와 실무 폴더의 차이
- 기능별 구조와 도메인별 구조
- 작은 프로젝트와 큰 프로젝트의 구조 선택
- 폴더 구조를 정할 때의 기준

## 폴더 구조는 약속이다

폴더 구조에는 절대 정답이 없다.

하지만 팀이 함께 일하려면 "어떤 파일을 어디에 둘지"에 대한 약속이 필요하다.

Nuxt는 기본 폴더를 제공한다.

```txt
pages/
components/
composables/
layouts/
plugins/
server/
stores/
utils/
```

실무에서는 여기에 프로젝트 성격에 맞는 폴더를 더하거나, 하위 구조를 정리한다.

## 작은 프로젝트 구조

작은 프로젝트는 단순한 구조가 좋다.

```txt
components/
  AppHeader.vue
  AppFooter.vue
  PostCard.vue

composables/
  useAuth.ts
  useApi.ts

pages/
  index.vue
  posts/
    index.vue
    [id].vue

server/
  api/
    posts.get.ts
```

초보 단계에서는 이 정도 구조로 충분하다.

괜히 복잡한 아키텍처를 먼저 도입하면 학습과 개발 속도가 느려질 수 있다.

## 기능별 구조

기능별 구조는 파일 종류에 따라 나누는 방식이다.

```txt
components/
  posts/
    PostCard.vue
    PostList.vue

composables/
  usePosts.ts

stores/
  post.ts

types/
  post.ts

pages/
  posts/
    index.vue
    [id].vue
```

Nuxt 기본 폴더 구조와 잘 맞고, 처음 이해하기 쉽다.

하지만 프로젝트가 커지면 하나의 기능이 여러 폴더에 흩어져 찾기 어려워질 수 있다.

## 도메인별 구조

도메인별 구조는 기능 단위로 관련 파일을 모으는 방식이다.

```txt
features/
  posts/
    components/
      PostCard.vue
      PostList.vue
    composables/
      usePosts.ts
    types.ts
    api.ts

pages/
  posts/
    index.vue
    [id].vue
```

게시글과 관련된 코드가 `features/posts`에 모여 있어 기능 단위로 이해하기 쉽다.

다만 Nuxt의 자동 import 규칙과 충돌하지 않도록 import 경로와 자동 등록 전략을 정해야 한다.

## components 구조

컴포넌트는 역할별로 나눌 수 있다.

```txt
components/
  base/
    BaseButton.vue
    BaseInput.vue
  layout/
    AppHeader.vue
    AppSidebar.vue
  posts/
    PostCard.vue
    PostList.vue
```

기준은 다음처럼 잡을 수 있다.

- `base`: 앱 전체 공통 UI
- `layout`: 레이아웃 구성 요소
- `posts`: 게시글 도메인 전용 컴포넌트

## server 구조

서버 API가 늘어나면 server 폴더도 정리해야 한다.

```txt
server/
  api/
    posts/
      index.get.ts
      index.post.ts
      [id].get.ts
      [id].put.ts
      [id].delete.ts
  middleware/
    auth.ts
  utils/
    requireUser.ts
    response.ts
```

API 주소와 폴더 구조를 맞추면 이해하기 쉽다.

```txt
GET /api/posts       -> server/api/posts/index.get.ts
GET /api/posts/1     -> server/api/posts/[id].get.ts
```

## types 폴더

공통 타입은 `types` 폴더에 둘 수 있다.

```txt
types/
  post.ts
  user.ts
  api.ts
```

사용할 때는 타입 전용 import를 사용한다.

```ts
import type { Post } from '~/types/post'
```

타입 파일이 너무 커지면 도메인별로 나눈다.

## 구조 선택 기준

다음 질문으로 구조를 정하자.

- 프로젝트 규모가 작은가, 큰가?
- 도메인이 몇 개인가?
- 팀원이 몇 명인가?
- 같은 기능 파일을 자주 함께 수정하는가?
- Nuxt 자동 import를 적극 활용할 것인가?
- 명시적 import를 선호하는가?

처음에는 단순하게 시작하고, 불편함이 반복될 때 구조를 개선하는 것이 좋다.

## 자주 하는 실수

처음부터 너무 복잡한 구조를 만드는 실수가 많다.

폴더가 많다고 좋은 구조가 아니다. 파일을 찾기 쉽고, 변경 범위가 자연스럽고, 팀이 이해할 수 있어야 좋은 구조다.

또 규칙 없이 사람마다 다른 위치에 파일을 만들면 프로젝트가 금방 흐트러진다.

## 정리

실무 폴더 구조는 팀의 약속이다. 작은 프로젝트는 Nuxt 기본 구조로 시작하고, 규모가 커지면 기능별 또는 도메인별 구조를 선택할 수 있다. 중요한 것은 파일을 찾기 쉽고 변경하기 쉬운 구조를 유지하는 것이다.
