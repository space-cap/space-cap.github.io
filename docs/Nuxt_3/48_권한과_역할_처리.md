# 권한과 역할 처리

## 이번 장에서 배울 것

- 역할과 권한의 차이
- 관리자 페이지 접근을 제한하는 방법
- UI 표시 제어와 서버 권한 검증의 차이
- 역할 기반 접근 제어의 기본 흐름

## 역할과 권한

역할은 사용자에게 붙이는 큰 분류다.

예를 들어 다음과 같은 역할이 있을 수 있다.

- guest
- user
- manager
- admin

권한은 어떤 행동을 할 수 있는지 나타낸다.

예를 들어 다음은 권한이다.

- 게시글 작성
- 게시글 삭제
- 사용자 목록 조회
- 관리자 설정 변경

작은 프로젝트에서는 역할만으로 충분할 수 있다. 규모가 커지면 역할과 권한을 분리해 관리하기도 한다.

## 사용자 정보에 role 넣기

현재 사용자 API가 역할 정보를 반환한다고 가정하자.

`server/api/auth/me.get.ts`

```ts
export default defineEventHandler((event) => {
  const session = getCookie(event, 'session')

  if (!session) {
    throw createError({
      statusCode: 401,
      statusMessage: '로그인이 필요합니다.'
    })
  }

  return {
    id: 1,
    name: '홍길동',
    role: 'admin'
  }
})
```

클라이언트는 이 정보를 이용해 메뉴 표시나 페이지 접근을 제어할 수 있다.

## 관리자 미들웨어 만들기

`middleware/admin.ts`

```ts
export default defineNuxtRouteMiddleware(async () => {
  const user = useState('auth-user', () => null)

  if (!user.value) {
    try {
      user.value = await $fetch('/api/auth/me')
    } catch {
      return navigateTo('/login')
    }
  }

  if (user.value?.role !== 'admin') {
    throw createError({
      statusCode: 403,
      statusMessage: '관리자 권한이 필요합니다.'
    })
  }
})
```

관리자 페이지에 적용한다.

```vue
<script setup>
definePageMeta({
  middleware: 'admin'
})
</script>

<template>
  <main>
    <h1>관리자 페이지</h1>
  </main>
</template>
```

## UI 표시 제어

역할에 따라 메뉴를 숨길 수 있다.

```vue
<script setup>
const user = useState('auth-user', () => null)
</script>

<template>
  <nav>
    <NuxtLink to="/">홈</NuxtLink>
    <NuxtLink v-if="user?.role === 'admin'" to="/admin">
      관리자
    </NuxtLink>
  </nav>
</template>
```

이 코드는 관리자에게만 관리자 메뉴를 보여 준다.

하지만 메뉴를 숨기는 것은 보안이 아니다. 사용자가 직접 `/admin` 주소를 입력할 수 있기 때문이다.

## 서버 API 권한 검증

관리자 API는 서버에서 다시 권한을 확인해야 한다.

`server/api/admin/users.get.ts`

```ts
export default defineEventHandler((event) => {
  const session = getCookie(event, 'session')

  const user = session
    ? { id: 1, role: 'admin' }
    : null

  if (!user) {
    throw createError({
      statusCode: 401,
      statusMessage: '로그인이 필요합니다.'
    })
  }

  if (user.role !== 'admin') {
    throw createError({
      statusCode: 403,
      statusMessage: '관리자 권한이 필요합니다.'
    })
  }

  return [
    { id: 1, name: '홍길동' }
  ]
})
```

실제 프로젝트에서는 세션 ID로 DB나 세션 저장소에서 사용자를 조회한 뒤 권한을 확인한다.

## 권한 확인 유틸 만들기

권한 검증이 반복되면 `server/utils`로 분리할 수 있다.

`server/utils/requireAdmin.ts`

```ts
export const requireAdmin = (event) => {
  const user = event.context.auth?.user

  if (!user) {
    throw createError({
      statusCode: 401,
      statusMessage: '로그인이 필요합니다.'
    })
  }

  if (user.role !== 'admin') {
    throw createError({
      statusCode: 403,
      statusMessage: '관리자 권한이 필요합니다.'
    })
  }

  return user
}
```

API에서는 다음처럼 사용한다.

```ts
export default defineEventHandler((event) => {
  const user = requireAdmin(event)

  return {
    ok: true,
    user
  }
})
```

## 401과 403의 차이

권한 처리에서 자주 쓰는 상태 코드는 401과 403이다.

| 상태 코드 | 의미 | 예시 |
| --- | --- | --- |
| 401 | 인증 필요 | 로그인하지 않음 |
| 403 | 권한 없음 | 로그인했지만 관리자가 아님 |

둘을 구분하면 클라이언트에서 더 정확한 메시지를 보여 줄 수 있다.

## 자주 하는 실수

가장 흔한 실수는 UI에서 버튼만 숨기고 서버 검증을 하지 않는 것이다.

버튼을 숨겨도 API 주소를 직접 호출할 수 있다. 삭제, 수정, 관리자 조회 같은 중요한 작업은 반드시 서버에서 권한을 확인해야 한다.

또 역할 이름을 여러 곳에 문자열로 흩뿌리면 유지보수가 어려워진다. 규모가 커지면 역할 상수나 권한 정책을 따로 정리하는 것이 좋다.

## 정리

역할은 사용자의 분류이고, 권한은 사용자가 할 수 있는 행동이다. Nuxt에서는 라우트 미들웨어로 페이지 접근을 제어하고, 서버 API에서 실제 권한을 검증해야 한다.
