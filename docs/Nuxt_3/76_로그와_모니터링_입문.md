# 로그와 모니터링 입문

## 이번 장에서 배울 것

- 로그와 모니터링이 필요한 이유
- 클라이언트 오류와 서버 오류를 구분하는 방법
- 운영에서 확인해야 할 기본 지표
- 오류 추적 도구를 도입할 때의 기준

## 로그란

로그는 앱이 실행되는 동안 남기는 기록이다.

예를 들어 다음 정보가 로그가 될 수 있다.

- 서버 API 요청
- 오류 메시지
- 로그인 실패
- 결제 실패
- 외부 API 응답 오류
- 배포 후 첫 실행 상태

개발 중에는 `console.log`로 충분할 수 있지만, 운영 환경에서는 더 체계적인 기록과 검색이 필요하다.

## 모니터링이란

모니터링은 앱이 정상적으로 동작하는지 지속적으로 관찰하는 일이다.

예를 들어 다음을 확인한다.

- 서버가 살아 있는가?
- 오류가 늘어나고 있는가?
- 응답 시간이 느려졌는가?
- 특정 API가 자주 실패하는가?
- 배포 후 문제가 증가했는가?

운영 서비스에서는 사용자가 알려 주기 전에 문제를 발견하는 것이 중요하다.

## 클라이언트 오류와 서버 오류

Nuxt 앱은 클라이언트와 서버 양쪽에서 오류가 발생할 수 있다.

클라이언트 오류:

- 브라우저 JavaScript 오류
- 화면 렌더링 오류
- 이벤트 핸들러 오류
- chunk loading 오류

서버 오류:

- `server/api` 오류
- 외부 API 호출 실패
- 인증 검증 실패
- DB 연결 오류
- SSR 렌더링 오류

운영 로그를 볼 때 오류가 어느 쪽에서 발생했는지 먼저 구분해야 한다.

## 서버 로그 남기기

서버 API에서 간단한 로그를 남길 수 있다.

```ts
export default defineEventHandler(async (event) => {
  const url = getRequestURL(event)

  console.log('API 요청:', url.pathname)

  return {
    ok: true
  }
})
```

개발 중에는 유용하지만, 운영에서는 민감한 정보를 로그에 남기지 않도록 주의해야 한다.

## 민감한 정보는 로그에 남기지 않기

다음 값은 로그에 남기면 안 된다.

- 비밀번호
- 인증 토큰
- 세션 ID
- 주민등록번호 같은 개인정보
- 결제 정보
- API secret

로그는 운영자나 외부 로그 서비스에 저장될 수 있다. 필요한 최소 정보만 남기는 것이 좋다.

## 요청 ID

문제가 생겼을 때 하나의 요청 흐름을 추적하려면 요청 ID가 도움이 된다.

서버 미들웨어에서 요청마다 ID를 만들고 context에 넣을 수 있다.

```ts
export default defineEventHandler((event) => {
  event.context.requestId = crypto.randomUUID()
})
```

API 로그에 requestId를 함께 남기면 관련 로그를 묶어 보기 쉬워진다.

## 확인할 기본 지표

운영 환경에서는 다음 지표를 살펴보면 좋다.

- 오류 수
- 4xx 응답 수
- 5xx 응답 수
- 평균 응답 시간
- 느린 API 목록
- 배포 직후 오류 증가 여부
- 사용자 브라우저 오류

처음부터 모든 것을 완벽하게 모니터링할 필요는 없다. 중요한 API와 핵심 사용자 흐름부터 시작한다.

## 오류 추적 도구

운영 서비스에서는 Sentry, Datadog, New Relic, Logtail 같은 오류 추적 또는 로그 수집 도구를 사용할 수 있다.

도구를 선택할 때는 다음을 확인한다.

- Nuxt 3와 잘 연동되는가?
- 클라이언트와 서버 오류를 모두 수집할 수 있는가?
- source map 처리를 지원하는가?
- 개인정보 마스킹을 설정할 수 있는가?
- 팀이 실제로 확인할 수 있는 알림 흐름이 있는가?

도구를 설치하는 것보다 중요한 것은 오류를 확인하고 대응하는 운영 습관이다.

## 알림 기준

모든 오류에 알림을 보내면 금방 무시하게 된다.

처음에는 다음 기준으로 알림을 설정할 수 있다.

- 5xx 오류가 일정 수 이상 발생
- 로그인 API 실패율 급증
- 결제 관련 API 실패
- 배포 직후 오류 급증
- 서버 응답 시간 급증

사용자에게 직접 영향을 주는 문제부터 알림을 받는 것이 좋다.

## 자주 하는 실수

운영 오류를 브라우저 콘솔에서만 확인하려는 실수가 있다.

사용자의 브라우저에서 발생한 오류는 개발자 컴퓨터의 콘솔에 보이지 않는다. 운영에서는 오류 수집 도구나 플랫폼 로그를 확인해야 한다.

또 로그에 너무 많은 정보를 남기면 비용과 보안 문제가 생길 수 있다.

## 정리

로그는 앱의 실행 기록이고, 모니터링은 앱이 정상 동작하는지 관찰하는 일이다. Nuxt 운영에서는 클라이언트 오류와 서버 오류를 구분하고, 민감한 정보를 로그에 남기지 않으며, 중요한 오류부터 추적하는 것이 좋다.
