# SI 프로젝트 수행 방법론

> 목표: SI 프로젝트가 어떤 문서와 절차로 진행되는지 이해하고, 개발자가 각 단계에서 무엇을 해야 하는지 정리한다.

## 1. 프로젝트는 요구사항에서 시작한다

SI 프로젝트는 고객의 요구사항을 시스템으로 구현하는 일이다.

요구사항은 처음부터 완벽하지 않다. 고객도 자신이 원하는 것을 정확히 모를 수 있고, 부서마다 원하는 것이 다를 수 있다.

그래서 SI 프로젝트에서는 요구사항을 듣고, 정리하고, 확인하고, 문서화하는 과정이 중요하다.

## 2. 전체 흐름

일반적인 SI 프로젝트 흐름은 다음과 같다.

```text
제안 -> 계약 -> 착수 -> 분석 -> 설계 -> 개발 -> 테스트 -> 데이터 이관 -> 오픈 -> 안정화 -> 유지보수
```

각 단계는 문서와 산출물로 이어진다.

## 3. 제안과 계약

### 3.1 RFP

RFP는 `Request For Proposal`의 약자다. 제안요청서라고 부른다.

고객이 원하는 시스템 범위, 일정, 조건을 정리한 문서다.

개발자는 RFP를 볼 때 다음을 확인한다.

- 구축 범위
- 필수 기능
- 연동 대상
- 데이터 이관 여부
- 사용자 수
- 오픈 일정
- 유지보수 조건

### 3.2 제안서와 견적서

제안서는 어떻게 구축할지 설명하는 문서이고, 견적서는 비용을 제시하는 문서다.

계약 이후에는 제안서와 견적서가 범위 판단의 근거가 될 수 있다.

## 4. 착수

착수 단계에서는 프로젝트를 공식적으로 시작한다.

주요 산출물은 다음과 같다.

- 착수보고서
- WBS
- 역할분담표
- 회의체 계획
- 이슈관리 양식
- 산출물 목록

`WBS`는 Work Breakdown Structure의 약자로, 일을 작은 단위로 나누고 일정과 담당자를 정리한 표다.

## 5. 분석

분석 단계에서는 고객의 현재 업무를 파악한다.

이를 `AS-IS 분석`이라고 한다.

### 5.1 확인할 것

- 현재 업무 절차
- 사용하는 엑셀 양식
- 기존 시스템 화면
- 부서별 역할
- 승인 절차
- 예외 상황
- 자주 발생하는 문제
- 현장 장비와 네트워크

### 5.2 현업 인터뷰

현업 인터뷰에서는 고객의 말을 바로 기능으로 번역하지 말고, 실제 업무 이벤트를 확인해야 한다.

예를 들어 "재고가 안 맞아요"라는 말은 다음 중 하나일 수 있다.

- 입고 처리가 누락됨
- 출고가 중복됨
- 창고 이동이 반영되지 않음
- 생산 투입이 재고에서 빠지지 않음
- 실사 조정 권한이 없음
- 조회 기준일이 다름

## 6. 설계

설계 단계에서는 앞으로 만들 시스템의 모습을 정리한다.

이를 `TO-BE 설계`라고 한다.

### 6.1 요구사항정의서

고객 요구를 기능 단위로 정리한 문서다.

좋은 요구사항은 다음 조건을 만족한다.

- 누가 사용하는지 명확하다.
- 어떤 조건에서 동작하는지 명확하다.
- 입력과 출력이 명확하다.
- 예외 상황이 적혀 있다.
- 테스트 가능한 형태다.

### 6.2 화면설계서

화면 구성과 동작을 설명한다.

포함할 내용은 다음과 같다.

- 화면명
- 메뉴 위치
- 검색 조건
- 목록 컬럼
- 입력 항목
- 버튼 동작
- 필수 값
- 권한
- 오류 메시지

### 6.3 ERD

ERD는 DB 테이블과 관계를 보여주는 문서다.

ERP/MES에서는 마스터 테이블과 트랜잭션 테이블의 관계를 이해하는 것이 중요하다.

### 6.4 인터페이스 정의서

시스템 간 연동을 정의한다.

송신/수신 시스템, 연동 방식, 항목, 주기, 실패 처리, 재처리 방법을 포함해야 한다.

## 7. 개발

개발 단계에서는 설계서를 기준으로 기능을 구현한다.

ERP/MES 개발에서는 다음 항목을 함께 봐야 한다.

- 화면
- 저장 로직
- 조회 쿼리
- 권한
- 출력물
- 엑셀 다운로드
- 로그
- 배치
- 외부 연동
- 기존 데이터 영향

기능 하나가 여러 곳에 영향을 줄 수 있으므로, 작은 수정도 영향 범위를 확인해야 한다.

## 8. 테스트

테스트는 개발자가 혼자 버튼을 눌러보는 것으로 끝나지 않는다.

| 테스트 | 목적 |
| --- | --- |
| 단위테스트 | 기능 단위 정상 동작 확인 |
| 통합테스트 | 여러 기능과 시스템 연결 확인 |
| 시나리오 테스트 | 실제 업무 흐름대로 처리되는지 확인 |
| UAT | 현업 사용자가 인수 가능 여부 확인 |
| 회귀 테스트 | 수정 후 기존 기능이 깨지지 않았는지 확인 |

ERP/MES 테스트는 정상 케이스보다 예외 케이스가 중요하다.

- 재고 부족
- 중복 등록
- 마감 이후 수정
- 권한 없음
- 연동 실패
- 부분 취소
- 반품

## 9. 데이터 이관

기존 엑셀이나 구 시스템 데이터를 새 시스템으로 옮긴다.

데이터 이관 절차는 보통 다음과 같다.

```text
이관 대상 정의
-> 데이터 추출
-> 정제
-> 매핑
-> 테스트 이관
-> 검증
-> 최종 이관
-> 오픈 후 확인
```

이관에서 가장 중요한 것은 코드 체계와 기준정보다.

## 10. 오픈과 안정화

오픈은 실제 업무를 새 시스템으로 전환하는 순간이다.

오픈 체크리스트는 다음과 같다.

- 최종 소스 반영
- DB 스키마 반영
- 기준정보 확인
- 초기 데이터 이관
- 사용자 계정과 권한
- 출력물 확인
- 연동 설정
- 백업
- 롤백 계획
- 담당자 연락망

안정화 기간에는 문의가 빠르게 들어온다. 이슈를 무작정 처리하지 말고 우선순위를 나누어야 한다.

## 11. 변경 요청 관리

프로젝트 중간에 새로운 요청이 나오면 변경 요청으로 관리한다.

변경 요청에는 다음을 적는다.

- 요청자
- 요청 내용
- 요청 사유
- 영향 범위
- 추가 비용 여부
- 일정 영향
- 승인자

개발자는 변경 요청을 감정적으로 받아들이지 말고, 영향 분석으로 대응해야 한다.

## 12. 이 문서에서 꼭 가져갈 것

SI 프로젝트는 코드보다 요구사항과 범위 관리가 먼저다.

입사자는 요구사항정의서, 화면설계서, ERD, 인터페이스 정의서, 테스트 결과서, WBS 같은 산출물 이름을 익히고, 각 문서가 개발과 운영에 어떻게 연결되는지 이해해야 한다.
