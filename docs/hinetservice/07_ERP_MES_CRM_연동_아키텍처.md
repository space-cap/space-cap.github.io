# ERP·MES·CRM 연동 아키텍처

> 목표: ERP, MES, CRM과 주변 시스템이 어떤 방식으로 데이터를 주고받는지 이해한다.

## 1. 업무 시스템은 혼자 존재하지 않는다

ERP, MES, CRM은 각각 역할이 있지만 실제 고객사에서는 서로 연결되어야 가치가 커진다.

예를 들어 쇼핑몰에서 주문이 들어오면 ERP에 수주가 생기고, 재고가 부족하면 생산계획이 잡히고, MES에서 생산실적이 올라오고, 출고 후 고객에게 알림톡이 발송될 수 있다.

```text
쇼핑몰 주문
-> ERP 수주
-> ERP 재고 확인
-> MES 작업지시
-> MES 생산실적
-> ERP 제품입고
-> ERP 출고
-> 택배 송장
-> CRM/알림톡 고객 안내
```

## 2. 기간계와 주변 시스템

업무 시스템을 볼 때 `기간계`와 `주변 시스템`을 구분하면 이해가 쉽다.

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 기간계 | 회사 핵심 거래와 기준 데이터를 관리하는 중심 시스템 | ERP |
| 현장계 | 제조 현장의 실행 데이터를 관리하는 시스템 | MES, POP |
| 고객계 | 고객 접점과 영업 활동을 관리하는 시스템 | CRM, 상담 시스템 |
| 주변 시스템 | 특정 업무를 보조하거나 외부와 연결 | POS, 택배, 쇼핑몰, 은행, 국세청 |

하이네트서비스의 공개 서비스는 ERP를 중심으로 주변 시스템을 많이 연동하는 구조로 이해할 수 있다.

## 3. 연동 방식의 종류

### 3.1 API 연동

HTTP 같은 표준 방식으로 데이터를 주고받는다.

예시는 다음과 같다.

- 알림톡 발송 API
- 택배 송장 등록 API
- 쇼핑몰 주문 수집 API
- 공공기관 신고 API

API 연동에서는 인증키, 요청 형식, 응답 형식, 실패 코드, 호출 제한을 확인해야 한다.

### 3.2 파일 연동

엑셀, CSV, TXT 파일을 업로드하거나 다운로드해서 데이터를 주고받는다.

장점은 단순하고 도입이 쉽다는 것이다. 단점은 실시간성이 낮고, 파일 형식이 깨지기 쉽다는 것이다.

### 3.3 DB 연동

다른 시스템의 DB를 직접 조회하거나, 중간 테이블을 통해 데이터를 주고받는다.

빠르고 편할 수 있지만 결합도가 높아진다. 상대 시스템 테이블 구조가 바뀌면 장애가 날 수 있다.

### 3.4 배치 연동

정해진 시간마다 데이터를 한꺼번에 처리한다.

예를 들어 매일 새벽 쇼핑몰 주문을 수집하거나, 은행 입금내역을 가져올 수 있다.

### 3.5 EDI 연동

정해진 표준 규격으로 기업 간 문서를 교환하는 방식이다. 대형 유통사, 제조사, 물류사와 거래할 때 등장할 수 있다.

## 4. 실시간과 배치

연동은 실시간일 수도 있고 배치일 수도 있다.

| 구분 | 실시간 | 배치 |
| --- | --- | --- |
| 처리 시점 | 이벤트 발생 즉시 | 정해진 시간 |
| 장점 | 최신 데이터 유지 | 안정적이고 관리 쉬움 |
| 단점 | 장애 영향이 즉시 발생 | 데이터 지연 |
| 예시 | POS 매출 반영, 알림톡 발송 | 일일 주문 수집, 월별 정산 |

무조건 실시간이 좋은 것은 아니다. 업무상 몇 시간 늦어도 되는 데이터는 배치가 더 안전할 수 있다.

## 5. 단방향과 양방향

연동 방향도 중요하다.

| 구분 | 설명 | 예시 |
| --- | --- | --- |
| 단방향 | 한 시스템에서 다른 시스템으로만 전달 | MES 실적을 ERP로 전송 |
| 양방향 | 서로 데이터를 주고받음 | ERP 작업지시 전송, MES 실적 수신 |

양방향 연동은 편리하지만 데이터 충돌 가능성이 있다. 어느 시스템이 원본인지 명확해야 한다.

## 6. 마스터 데이터와 트랜잭션 데이터

연동 데이터는 크게 마스터와 트랜잭션으로 나뉜다.

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 마스터 | 기준이 되는 데이터 | 거래처, 품목, 창고, 공정, 설비 |
| 트랜잭션 | 실제 업무 이벤트 | 수주, 입고, 출고, 작업실적, 검사결과 |

마스터 데이터가 맞지 않으면 트랜잭션 연동이 실패한다.

예를 들어 MES에서 생산실적을 ERP로 보내는데 ERP에 해당 품목코드가 없으면 반영할 수 없다.

## 7. 데이터 원천과 정합성

연동 설계에서 가장 중요한 질문은 "어느 시스템이 원천인가"다.

예를 들어 품목 기준정보는 ERP가 원천일 가능성이 높다. 작업실적은 MES가 원천일 가능성이 높다. 상담이력은 CRM이 원천일 가능성이 높다.

| 데이터 | 원천 시스템 후보 |
| --- | --- |
| 거래처 | ERP 또는 CRM |
| 품목 | ERP |
| 생산계획 | ERP |
| 작업지시 | ERP 또는 MES |
| 생산실적 | MES |
| 검사결과 | MES 또는 QMS |
| 출고 | ERP 또는 WMS |
| 상담이력 | CRM |

원천이 불명확하면 같은 데이터를 여러 곳에서 수정하게 되고 정합성이 깨진다.

## 8. 연동 장애 유형

자주 생기는 장애는 다음과 같다.

- 인증 실패
- 네트워크 오류
- 상대 API 변경
- 필수 값 누락
- 코드 매핑 오류
- 중복 전송
- 일부 성공 후 일부 실패
- 시간 차이로 인한 데이터 누락
- 특수문자나 인코딩 문제
- 대량 데이터 처리 지연

연동 기능에는 반드시 로그와 재처리 기능이 필요하다.

## 9. 인터페이스 명세서에서 봐야 할 것

인터페이스 명세서를 볼 때는 다음 항목을 확인한다.

- 인터페이스 이름
- 송신 시스템
- 수신 시스템
- 처리 주기
- 연동 방식
- 요청 항목
- 응답 항목
- 필수 여부
- 코드 매핑
- 성공/실패 기준
- 재처리 방법
- 담당자

명세서가 없으면 장애가 났을 때 책임 소재와 처리 방법이 불분명해진다.

## 10. 하이네트서비스 공개 서비스와 연결해 보기

공개 서비스 기준으로 예상 가능한 연동은 다음과 같다.

| 서비스 | 연동 관점 |
| --- | --- |
| PDA/바코드 | 입출고, 실사, 생산현장 데이터 입력 |
| POS | 매장 매출을 ERP 매출/재고로 반영 |
| 쇼핑몰/B2B | 주문 수집, 납품업체 발주 공유 |
| 택배연동 | 송장 출력, 운송장번호 저장, 배송 추적 |
| 전화연동 | 발신자 고객정보 표시, 상담 처리 |
| 은행연동 | 입출금 내역 조회, 전표 연동 |
| 오픈마켓 연동 | 주문 수집, 매출전표 생성, 송장번호 전송 |
| 모바일 연동 | 주문, 재고, 원장, 품목 조회 |
| 국세청연동 | 매입세금계산서, 휴폐업 조회, 카드 사용내역 |
| 카카오 알림톡 | 배송, AS, 안내 메시지 발송 |
| 식약처/축산물이력제 | 공공기관 신고와 이력정보 관리 |

## 11. 이 문서에서 꼭 가져갈 것

연동은 단순히 데이터를 보내는 기능이 아니다. 업무 흐름, 원천 시스템, 실패 처리, 재처리, 로그, 정합성까지 함께 설계해야 한다.

입사 초기에는 "이 데이터의 원천은 어디인가", "언제 전송되는가", "실패하면 어떻게 재처리하는가" 세 질문을 습관처럼 던지면 좋다.
