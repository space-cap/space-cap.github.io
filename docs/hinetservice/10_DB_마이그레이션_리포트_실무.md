# DB·마이그레이션·리포트 실무

> 목표: ERP/MES 업무 시스템에서 DB, 데이터 이관, 리포트가 왜 중요한지 이해한다.

## 1. 업무 시스템에서 DB가 중요한 이유

ERP와 MES는 결국 업무 데이터를 저장하고 조회하는 시스템이다.

화면은 사용자가 보는 입구이고, DB는 실제 업무 기록이 남는 장소다.

개발자는 화면 오류를 고칠 때도 DB 흐름을 알아야 한다.

- 어떤 테이블에 저장되는가
- 헤더와 상세가 어떻게 연결되는가
- 상태값은 무엇인가
- 삭제는 실제 삭제인가
- 마감 데이터는 수정 가능한가
- 집계 화면은 어떤 기준으로 계산하는가

## 2. 마스터와 트랜잭션

업무 DB는 크게 마스터와 트랜잭션으로 나눌 수 있다.

| 구분 | 설명 | 예시 |
| --- | --- | --- |
| 마스터 | 기준이 되는 데이터 | 거래처, 품목, 창고, 공정, 설비 |
| 트랜잭션 | 실제 업무 이벤트 데이터 | 수주, 발주, 입고, 출고, 작업실적 |

마스터가 틀리면 트랜잭션도 틀어진다.

예를 들어 품목의 단위가 잘못 등록되면 입고, 출고, 생산, 재고, 원가가 모두 영향을 받을 수 있다.

## 3. 헤더와 상세

ERP/MES 테이블은 헤더와 상세 구조가 많다.

예를 들어 수주 데이터는 다음처럼 나뉠 수 있다.

```text
수주 헤더: 수주번호, 거래처, 수주일자, 담당자, 상태
수주 상세: 수주번호, 품목, 수량, 단가, 금액, 납기
```

헤더는 문서 전체 정보이고, 상세는 품목별 라인 정보다.

개발자는 헤더만 수정하고 상세를 놓치거나, 상세 합계와 헤더 금액이 불일치하지 않도록 주의해야 한다.

## 4. 상태값

업무 데이터는 단순히 존재 여부만 중요한 것이 아니다. 상태값이 중요하다.

예시는 다음과 같다.

- 임시저장
- 확정
- 승인대기
- 승인완료
- 출고완료
- 매출완료
- 취소
- 삭제
- 마감

상태값을 잘못 바꾸면 업무 흐름이 깨진다.

운영 DB를 수정해야 할 때는 상태값의 의미와 후속 데이터 영향을 반드시 확인해야 한다.

## 5. 데이터 이관

데이터 이관은 기존 시스템이나 엑셀 데이터를 새 시스템으로 옮기는 작업이다.

단순 복사가 아니라 데이터 정리와 업무 기준 통일이 함께 필요하다.

### 5.1 이관 대상

자주 이관하는 데이터는 다음과 같다.

- 거래처
- 품목
- 창고
- 사용자
- 초기 재고
- 미수금
- 미지급금
- 수주 잔량
- 발주 잔량
- 생산 중 작업
- 과거 매출/매입 자료

### 5.2 이관 절차

```text
대상 정의
-> 원본 데이터 확보
-> 컬럼 매핑
-> 코드 정리
-> 오류 데이터 정제
-> 테스트 이관
-> 고객 검증
-> 최종 이관
```

### 5.3 자주 생기는 문제

- 거래처명이 중복됨
- 사업자번호가 비어 있음
- 품목 단위가 다름
- 창고 코드가 없음
- 날짜 형식이 제각각임
- 숫자에 쉼표나 문자 값이 섞임
- 과거 퇴사자가 담당자로 들어 있음
- 재고 수량은 있는데 금액이 없음

이관 전에 고객과 데이터 정리 기준을 합의해야 한다.

## 6. 리포트와 출력물

ERP/MES에서 리포트는 매우 중요하다.

고객은 시스템에 입력한 데이터를 결국 보고서와 출력물로 확인한다.

자주 만나는 출력물은 다음과 같다.

- 견적서
- 발주서
- 거래명세서
- 세금계산서 관련 자료
- 재고현황
- 매입매출장
- 거래처별 원장
- 생산일보
- 작업지시서
- 검사성적서
- 바코드 라벨

## 7. 리포트 수정 시 확인할 것

리포트 수정은 단순한 디자인 작업이 아니다.

다음 항목을 확인해야 한다.

- 조회 기준일
- 거래처 기준
- 품목 기준
- 창고 기준
- 부가세 포함 여부
- 취소 데이터 포함 여부
- 마감 데이터 기준
- 소수점 처리
- 합계 계산 방식
- 출력 권한

특히 금액과 수량이 들어가는 리포트는 고객 업무와 회계에 직접 영향을 준다.

## 8. 운영 DB 직접 수정이 위험한 이유

운영 DB 수정은 마지막 수단이어야 한다.

이유는 다음과 같다.

- 관련 테이블을 함께 수정하지 않으면 정합성이 깨진다.
- 이력 로그가 남지 않을 수 있다.
- 마감 데이터가 바뀔 수 있다.
- 회계 전표와 불일치할 수 있다.
- 같은 문제가 다시 발생할 수 있다.

불가피하게 수정해야 한다면 다음을 지킨다.

1. 원인 분석
2. 수정 대상 조회
3. 백업
4. 승인 확인
5. 수정 SQL 검토
6. 트랜잭션 처리
7. 수정 후 검증
8. 기록 남기기

## 9. 백업과 복구

업무 시스템에서는 백업이 생명줄이다.

확인할 내용은 다음과 같다.

- 백업 주기
- 백업 위치
- 보관 기간
- 복구 테스트 여부
- 배포 전 백업 여부
- 이관 전 백업 여부

백업이 있어도 복구해 본 적이 없다면 안심할 수 없다.

## 10. 이 문서에서 꼭 가져갈 것

ERP/MES 개발자는 DB를 두려워하면 안 되지만, 함부로 다뤄서도 안 된다.

마스터와 트랜잭션, 헤더와 상세, 상태값, 이관, 리포트, 백업을 이해하면 업무 시스템의 많은 문제가 보이기 시작한다.
