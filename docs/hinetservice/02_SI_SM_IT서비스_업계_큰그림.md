# SI·SM·IT서비스 업계 큰 그림

> 목표: SI, SM, 솔루션 구축, 유지보수의 차이를 이해하고 프로젝트가 어떤 흐름으로 진행되는지 파악한다.

## 1. SI란 무엇인가

SI는 `System Integration`의 약자다. 말 그대로 여러 업무, 시스템, 데이터, 장비, 외부 서비스를 하나의 업무 흐름으로 통합하는 일이다.

고객사는 보통 이런 문제를 가지고 있다.

- 엑셀로 관리하던 업무가 커져서 통제가 안 된다.
- 재고와 매출 숫자가 맞지 않는다.
- 생산 현장의 실적을 실시간으로 보고 싶다.
- 쇼핑몰 주문, 택배 송장, 세금계산서 처리를 자동화하고 싶다.
- 기존 ERP가 있지만 회사 업무와 맞지 않아 수정이 필요하다.

SI 프로젝트는 이런 문제를 분석해서 시스템으로 해결하는 과정이다.

## 2. SM과 유지보수란 무엇인가

SM은 `System Management` 또는 `System Maintenance`라는 의미로 쓰인다. 이미 구축된 시스템을 운영하고 관리하는 일이다.

SI가 집을 새로 짓거나 리모델링하는 일이라면, SM은 그 집의 전기, 수도, 보일러, 문고리를 계속 점검하고 고치는 일에 가깝다.

업무 시스템에서 SM은 다음 일을 포함한다.

- 오류 문의 대응
- 데이터 확인
- 기능 개선
- 권한 변경
- 출력물 수정
- 배치 작업 확인
- 서버와 DB 상태 확인
- 패치 배포
- 장애 보고

업무 시스템 회사에서는 신규 구축보다 운영·유지보수에서 고객 신뢰가 만들어지는 경우가 많다.

## 3. 솔루션 구축과 맞춤 개발의 차이

ERP/MES 업계에서는 완전히 새로 만드는 개발보다 기존 솔루션을 고객 업무에 맞춰 적용하는 일이 많다.

| 구분 | 설명 | 장점 | 주의점 |
| --- | --- | --- | --- |
| 패키지 도입 | 표준 제품을 거의 그대로 사용 | 빠른 도입, 비용 예측 쉬움 | 고객 업무와 안 맞을 수 있음 |
| 솔루션 커스터마이징 | 기존 제품을 수정 개발 | 제품 안정성과 업무 적합성 균형 | 고객별 차이가 쌓이면 복잡해짐 |
| 완전 맞춤 개발 | 고객 요구에 맞춰 처음부터 개발 | 업무에 딱 맞음 | 비용, 일정, 유지보수 부담 큼 |
| 연동 구축 | 기존 시스템끼리 연결 | 업무 자동화 효과 큼 | 장애와 데이터 정합성 관리 필요 |

하이네트서비스 업무는 기존 제품 기반 커스터마이징과 연동 구축의 비중이 높을 가능성이 있다.

## 4. SI 프로젝트의 이해관계자

SI 프로젝트에는 여러 사람이 등장한다.

| 역할 | 의미 | 개발자가 알아야 할 점 |
| --- | --- | --- |
| 고객사 | 시스템을 도입하는 회사 | 실제 업무를 가장 잘 안다 |
| 현업 | 시스템을 매일 사용할 부서 | 요구사항의 출발점이다 |
| 의사결정자 | 비용과 범위를 결정하는 사람 | 우선순위와 승인 권한이 있다 |
| PM | 프로젝트 총괄 책임자 | 일정, 범위, 리스크를 관리한다 |
| PL | 개발 리더 또는 파트 리더 | 설계와 개발 방향을 잡는다 |
| 개발자 | 기능 구현 담당자 | 업무 이해와 기술 구현을 연결한다 |
| 운영자 | 오픈 후 시스템 관리 담당자 | 유지보수성과 로그가 중요하다 |
| 외부 연동사 | 택배, 쇼핑몰, VAN, 공공 API 등 | 명세 변경과 장애 대응이 필요하다 |

좋은 개발자는 "요청한 사람"만 보지 않고 "이 기능을 실제로 쓰는 사람"을 같이 본다.

## 5. 프로젝트 생명주기

일반적인 SI 프로젝트는 다음 흐름으로 진행된다.

### 5.1 제안과 계약

고객 요구를 듣고 제안서와 견적서를 만든다. 이 단계에서 범위가 대략 정해진다.

개발자가 직접 참여하지 않더라도, 나중에 "계약 범위에 포함되는지"가 중요한 쟁점이 된다.

### 5.2 착수

프로젝트를 공식적으로 시작한다.

주요 산출물은 다음과 같다.

- 착수보고서
- 일정표
- WBS
- 역할분담표
- 커뮤니케이션 채널
- 이슈 관리 방식

### 5.3 분석

고객의 현재 업무를 파악한다. 이를 `AS-IS 분석`이라고 한다.

이 단계에서는 현업 인터뷰, 기존 문서 확인, 엑셀 양식 확인, 기존 시스템 확인, 현장 방문이 이루어진다.

### 5.4 설계

앞으로 바뀔 업무 흐름을 설계한다. 이를 `TO-BE 설계`라고 한다.

주요 산출물은 다음과 같다.

- 요구사항정의서
- 프로세스 정의서
- 화면설계서
- ERD
- 인터페이스 정의서
- 권한 정의서
- 출력물 정의서

### 5.5 개발

설계된 내용을 실제 시스템으로 만든다.

ERP/MES에서는 화면 개발, 쿼리 작성, 저장 로직, 리포트, 배치, 연동, 권한, 로그가 함께 움직인다.

### 5.6 테스트

테스트는 여러 단계가 있다.

| 테스트 | 목적 |
| --- | --- |
| 단위테스트 | 개발자가 기능 하나가 동작하는지 확인 |
| 통합테스트 | 여러 기능과 시스템이 함께 동작하는지 확인 |
| 사용자테스트 | 실제 현업이 업무 시나리오대로 써 보는 단계 |
| 오픈 리허설 | 실제 오픈처럼 데이터 이관과 배포를 연습 |

### 5.7 오픈과 안정화

시스템을 실제 업무에 적용한다. 이 시기를 `Go-Live`라고도 한다.

오픈 직후에는 문의가 몰린다. 사용자가 익숙하지 않은 문제도 있고, 실제 데이터에서만 드러나는 오류도 있다.

안정화 기간에는 빠른 대응이 중요하지만, 임시 수정을 남발하면 이후 운영이 어려워진다.

## 6. SI 업계에서 자주 생기는 리스크

### 6.1 범위 변경

고객은 프로젝트 중간에 새로운 요구를 말할 수 있다. 이를 `변경 요청`이라고 한다.

작은 요청처럼 보여도 DB, 화면, 출력물, 연동, 테스트에 영향을 줄 수 있다.

개발자는 "가능합니다"라고 바로 답하기보다 영향 범위를 먼저 확인해야 한다.

### 6.2 일정 압박

ERP/MES 프로젝트는 고객사의 실제 업무 일정과 연결된다.

- 월말 마감
- 회계 결산
- 공장 가동 일정
- 신규 창고 오픈
- 정부지원사업 점검
- 쇼핑몰 성수기

이런 일정 때문에 개발 일정이 빡빡해질 수 있다.

### 6.3 데이터 이관

기존 엑셀이나 구 시스템 데이터를 새 시스템으로 옮기는 일은 생각보다 어렵다.

문제는 보통 다음에서 생긴다.

- 품목코드가 중복됨
- 거래처명이 제각각임
- 필수 값이 비어 있음
- 단위가 다름
- 과거 데이터와 현재 업무 규칙이 다름
- 재고 수량과 금액이 맞지 않음

데이터 이관은 기술 작업이면서 동시에 업무 정리 작업이다.

### 6.4 현업 커뮤니케이션

현업은 개발 용어를 모르고, 개발자는 현업 용어를 모를 수 있다.

예를 들어 현업이 "출고가 안 돼요"라고 하면 개발자는 다음을 구분해야 한다.

- 출고 버튼이 비활성화된 것인가
- 출고 전표 저장 중 오류가 난 것인가
- 재고 부족으로 막힌 것인가
- 송장 출력이 안 되는 것인가
- 출고는 됐지만 매출 반영이 안 된 것인가

좋은 질문이 좋은 분석의 시작이다.

## 7. 입사자가 기억해야 할 태도

SI/SM 업무에서는 기술 실력만큼 업무 이해와 기록 습관이 중요하다.

- 고객 말을 그대로 믿기보다 업무 흐름으로 재해석한다.
- 모르는 용어는 즉시 적고 확인한다.
- DB를 보기 전에 업무 이벤트를 먼저 추적한다.
- 운영 데이터 수정은 항상 백업과 승인 여부를 확인한다.
- 한 번 해결한 장애는 재발 방지 관점으로 정리한다.
- 회의 내용과 결정사항은 문서로 남긴다.

## 8. 이 문서에서 꼭 가져갈 것

SI는 고객 업무를 시스템으로 구현하는 프로젝트이고, SM은 구현된 시스템을 안정적으로 운영하는 일이다.

ERP/MES 업계에서는 고객 업무, 데이터, 화면, 출력물, 외부 연동이 강하게 연결되어 있다. 그래서 개발자는 단순히 코드를 작성하는 사람이 아니라, 업무 흐름을 이해하고 시스템의 결과까지 책임지는 사람에 가깝다.
