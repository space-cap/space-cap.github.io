# 운영·유지보수·장애 대응

> 목표: 구축 이후 시스템 운영 업무가 어떤 모습인지, 장애와 고객 문의를 어떻게 처리해야 하는지 이해한다.

## 1. 운영 업무란 무엇인가

운영은 이미 오픈된 시스템이 매일 안정적으로 돌아가도록 관리하는 일이다.

ERP/MES는 고객사의 실제 업무와 연결되어 있기 때문에 장애가 나면 매출, 출고, 생산, 회계 마감에 영향을 줄 수 있다.

운영 업무에는 다음이 포함된다.

- 오류 문의 대응
- 사용법 안내
- 데이터 확인
- 기능 개선
- 권한 변경
- 출력물 수정
- 연동 실패 확인
- 배치 작업 확인
- 패치 배포
- 장애 보고

## 2. 고객 문의 유형

고객 문의는 대략 다음 유형으로 나눌 수 있다.

| 유형 | 예시 |
| --- | --- |
| 사용법 문의 | "이 화면에서 출고 취소는 어떻게 하나요?" |
| 오류 문의 | "저장 버튼을 누르면 오류가 납니다." |
| 데이터 문의 | "재고 수량이 실제와 다릅니다." |
| 권한 문의 | "메뉴가 보이지 않습니다." |
| 출력물 문의 | "거래명세서에 항목을 추가해 주세요." |
| 연동 문의 | "쇼핑몰 주문이 안 들어옵니다." |
| 개선 요청 | "검색 조건을 하나 더 넣어 주세요." |

문의 유형을 먼저 구분하면 대응 속도가 빨라진다.

## 3. 장애 등급

모든 문제가 같은 우선순위는 아니다.

| 등급 | 설명 | 예시 |
| --- | --- | --- |
| 긴급 | 업무 전체가 중단됨 | 로그인 불가, 출고 전체 불가, 생산실적 등록 불가 |
| 높음 | 핵심 업무 일부가 막힘 | 특정 거래처 출고 오류, 송장 전송 실패 |
| 보통 | 우회 가능하지만 수정 필요 | 특정 조회 조건 오류, 출력물 일부 항목 누락 |
| 낮음 | 개선 요청 또는 불편 사항 | 버튼 위치 변경, 화면 문구 수정 |

장애 등급을 정하면 지금 당장 처리해야 하는 일과 나중에 처리해도 되는 일을 구분할 수 있다.

## 4. 장애 대응 절차

장애 대응은 다음 순서로 진행한다.

```text
접수 -> 현상 확인 -> 영향 범위 파악 -> 임시 조치 -> 원인 분석 -> 수정 -> 검증 -> 배포 -> 재발 방지 기록
```

### 4.1 현상 확인

고객이 말한 증상을 그대로 믿기보다 재현 가능한 형태로 정리한다.

- 어떤 사용자에게 발생하는가
- 어떤 메뉴에서 발생하는가
- 어떤 조건으로 조회했는가
- 언제부터 발생했는가
- 오류 메시지는 무엇인가
- 다른 사용자는 정상인가

### 4.2 영향 범위 파악

장애가 전체인지 일부인지 확인한다.

- 전체 고객인가
- 특정 고객사인가
- 특정 사용자만인가
- 특정 메뉴만인가
- 특정 시간대만인가
- 외부 연동만인가

### 4.3 임시 조치

업무가 멈춘 경우 임시 조치가 필요할 수 있다.

예를 들어 송장 전송 API가 실패하면 임시로 파일 업로드 방식으로 처리할 수 있다.

단, 임시 조치는 반드시 기록하고 나중에 정리해야 한다.

## 5. 원인 분석 방법

원인은 크게 나눠서 본다.

| 영역 | 확인할 것 |
| --- | --- |
| 사용자 입력 | 필수 값 누락, 잘못된 코드, 권한 |
| 데이터 | 중복, 누락, 상태값 오류, 마감 |
| 프로그램 | 로직 오류, 예외 처리 누락 |
| DB | 쿼리 오류, 락, 성능, 인덱스 |
| 연동 | API 장애, 인증 실패, 응답 형식 변경 |
| 인프라 | 서버, 네트워크, 디스크, 백업 |

로그가 있다면 로그부터 확인하되, 로그만 믿지 말고 업무 데이터와 함께 봐야 한다.

## 6. 고객 커뮤니케이션

장애 대응에서 커뮤니케이션은 중요하다.

좋은 응답은 짧고 명확하다.

```text
현재 출고 저장 오류를 확인했습니다.
특정 품목의 재고 상태값 때문에 발생하는 것으로 보이며, 영향 범위 확인 후 30분 내 1차 조치 결과를 공유드리겠습니다.
```

피해야 할 응답은 다음과 같다.

- "저희 쪽 문제는 아닌 것 같습니다."
- "잠시만요."만 반복
- 원인 확인 전 단정
- 처리 시간을 말하지 않음
- 수정 후 결과를 공유하지 않음

## 7. 패치와 배포

운영 시스템에 수정 사항을 반영할 때는 신중해야 한다.

확인할 것은 다음과 같다.

- 수정 내용
- 영향 메뉴
- DB 변경 여부
- 배포 시간
- 사용자 공지 필요 여부
- 백업 여부
- 롤백 방법
- 배포 후 확인 항목

작은 수정이라도 운영 반영 기록을 남겨야 한다.

## 8. 장애 보고서

중요 장애는 보고서를 남긴다.

포함할 내용은 다음과 같다.

- 발생 일시
- 접수 일시
- 장애 내용
- 영향 범위
- 원인
- 임시 조치
- 최종 조치
- 재발 방지 대책
- 담당자

장애 보고서는 책임 추궁 문서가 아니라 다음 장애를 줄이는 학습 문서다.

## 9. 유지보수에서 좋은 습관

- 고객 문의를 업무 흐름으로 다시 정리한다.
- 재현 조건을 반드시 남긴다.
- 운영 데이터 수정 전 백업과 승인을 확인한다.
- 같은 문의가 반복되면 매뉴얼이나 기능 개선을 제안한다.
- 수정 후 고객이 실제 업무를 완료했는지 확인한다.
- 장애 원인을 개인 기억에 맡기지 말고 기록한다.

## 10. 이 문서에서 꼭 가져갈 것

운영·유지보수는 시스템을 매일 살아 있게 만드는 일이다.

개발자는 오류를 고치는 사람을 넘어, 고객 업무가 다시 정상 흐름으로 돌아갔는지 확인하는 사람이어야 한다.
