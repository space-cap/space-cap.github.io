# 코드 편집과 탐색

> 작성 기준일: 2026-05-19  
> 대상 독자: 기존 Delphi 코드에서 원하는 위치를 빠르게 찾고 싶은 사람  
> 목표: Code Editor, Code Insight, 검색, 선언 이동, 클래스 완성 기능을 실무 유지보수 흐름에 맞게 익힌다.

## 1. Delphi 코드는 찾는 능력이 절반이다

기존 업무 프로그램을 유지보수할 때 가장 먼저 필요한 능력은 "어디를 고쳐야 하는지 찾는 능력"이다.

Delphi 프로젝트는 Form, DataModule, 공통 unit, 패키지, 쿼리 코드가 섞여 있을 수 있다. 그래서 코드를 무작정 위에서 아래로 읽는 방식은 오래 걸린다.

실무 탐색 흐름은 보통 이렇다.

```text
화면에서 버튼/메뉴/그리드 찾기
-> Object Inspector에서 이벤트 찾기
-> 이벤트 핸들러로 이동
-> 호출하는 메서드 따라가기
-> SQL/DB/공통 함수 찾기
-> 수정 위치 결정
```

IDE의 코드 편집 기능은 이 흐름을 빠르게 만들어준다.

## 2. Code Editor 기본

`Code Editor`는 `.pas`, `.dpr`, `.dpk` 같은 Delphi 소스 파일을 편집하는 곳이다.

처음 자주 쓰는 작업:

| 작업 | 목적 |
| --- | --- |
| 파일 탭 전환 | Form unit, DataModule unit 오가기 |
| 검색 | 메서드, SQL, 문구 찾기 |
| 선언 이동 | 메서드/클래스 정의로 이동 |
| 자동 완성 | property, method 이름 빠르게 입력 |
| 오류 위치 이동 | Messages 창에서 오류 줄로 이동 |
| 북마크 | 자주 보는 위치 표시 |

Code Editor를 잘 쓰면 "어디 있지?"에 쓰는 시간이 줄어든다.

## 3. Code Insight란?

공식 문서 기준 Code Insight는 Code Editor 안에 포함된 기능 묶음이다. 코드 완성, 파라미터 표시, 코드 힌트, Tooltip Insight, 선언 이동, Class Completion, Error Insight 등이 여기에 들어간다.

Delphi에서는 Code Insight에 LSP(Language Server Protocol)를 사용한다고 공식 문서가 설명한다.

처음 익힐 기능:

| 기능 | 기본 단축키/동작 | 역할 |
| --- | --- | --- |
| Code Completion | `Ctrl+Space` | 자동 완성 목록 |
| Parameter Completion | `Ctrl+Shift+Space` | 메서드 파라미터 힌트 |
| Find Declaration | `Ctrl+Click` | 선언 위치로 이동 |
| Class Completion | `Ctrl+Shift+C` | 선언한 메서드 구현 생성 |
| Tooltip Insight | 마우스 올리기 | 타입/심볼 정보 확인 |
| Error Insight | 편집 중 오류 표시 | 문법/참조 문제 확인 |

단축키는 IDE 버전과 키맵에 따라 다를 수 있다. 회사에서 쓰는 키맵이 있으면 그 기준을 따른다.

## 4. Code Completion

Code Completion은 자동 완성 기능이다. 공식 문서에 따르면 Delphi와 C++에서 `Ctrl+Space`로 호출할 수 있고, 자동 호출이 꺼져 있어도 단축키로 실행할 수 있다.

예:

```pascal
edtName.
```

여기서 자동 완성을 열면 `Text`, `Clear`, `SetFocus`, `Enabled`, `Visible` 같은 멤버를 찾을 수 있다.

처음에는 자동 완성을 단순 입력 보조가 아니라 탐색 도구로 쓰면 좋다.

```text
이 컴포넌트가 어떤 property와 method를 갖고 있는가?
```

이 질문에 답해주는 도구이기 때문이다.

## 5. Parameter Completion

메서드를 호출할 때 파라미터가 헷갈리면 Parameter Completion을 쓴다.

예:

```pascal
FormatDateTime(
```

이때 파라미터 힌트를 보면 어떤 순서로 값을 넣어야 하는지 알 수 있다.

실무에서 유용한 경우:

- `Format`
- `StringReplace`
- DB Query 관련 메서드
- 회사 공통 함수
- 리포트/출력 함수

공통 함수는 이름만 보고 파라미터 의미가 애매한 경우가 많다. Parameter Completion은 이런 코드를 읽는 데 도움이 된다.

## 6. Find Declaration

Find Declaration은 심볼의 선언 위치로 이동하는 기능이다.

공식 Code Insight 문서에서는 `Ctrl+Click`으로 Go To Definition/Find Declaration 계열 기능을 사용할 수 있다고 설명한다.

예:

```pascal
SaveCustomer(CustomerId);
```

`SaveCustomer`로 이동하면 이 메서드가 어디에 선언/구현되어 있는지 찾을 수 있다.

탐색할 때 자주 쓰는 대상:

| 대상 | 찾는 이유 |
| --- | --- |
| 메서드 | 실제 로직 확인 |
| 클래스 | 어떤 책임을 가진 객체인지 확인 |
| property | 값이 어디서 읽히고 쓰이는지 확인 |
| 상수 | 코드값 의미 확인 |
| 타입 | DTO/레코드/열거형 구조 확인 |
| unit | 어느 파일에 있는지 확인 |

## 7. Class Completion

Class Completion은 클래스 선언부에 메서드만 먼저 적고 구현부를 자동 생성하는 기능이다.

예:

```pascal
type
  TMainForm = class(TForm)
  private
    procedure ValidateInput;
  end;
```

여기서 Class Completion을 실행하면 IDE가 `implementation` 영역에 구현 뼈대를 만든다.

```pascal
procedure TMainForm.ValidateInput;
begin

end;
```

공식 Code Insight 문서에서는 Class Completion 단축키를 `Ctrl+Shift+C`로 안내한다.

이 기능은 오타를 줄여준다. 직접 메서드 시그니처를 복사하다 보면 클래스 이름, 파라미터, 반환 타입을 틀리기 쉽다.

## 8. 검색 기본

대형 Delphi 프로젝트에서 검색은 매우 중요하다.

자주 검색하는 문자열:

| 찾을 것 | 검색어 예 |
| --- | --- |
| 버튼 이벤트 | `btnSaveClick` |
| 화면 문구 | `저장되었습니다` |
| SQL 테이블 | `CUSTOMER_MST` |
| 필드명 | `CUSTOMER_ID` |
| 공통 함수 | `ShowError`, `ExecQuery` |
| 메뉴 코드 | `MENU_CUSTOMER` |
| 에러 메시지 | 운영에서 캡처한 문구 |

검색 범위는 상황에 따라 다르게 잡는다.

| 범위 | 언제 쓰나 |
| --- | --- |
| 현재 파일 | 지금 보고 있는 unit 안에서 찾기 |
| 열린 파일 | 관련 파일 몇 개만 볼 때 |
| 프로젝트 | 현재 프로젝트 전체에서 찾기 |
| 폴더 전체 | Project Group 밖 공통 라이브러리까지 찾을 때 |

IDE 검색이 느리거나 누락될 때는 외부 도구의 `ripgrep`, Git 검색, 파일 탐색기 검색을 함께 쓴다.

## 9. Search Results 읽기

검색 결과는 무작정 위에서부터 열지 않는다.

먼저 파일명을 보고 분류한다.

```text
MainFormUnit.pas        -> 화면 코드일 가능성
CustomerRepository.pas  -> DB 접근 코드일 가능성
CommonUtils.pas         -> 공통 함수일 가능성
ReportForm.dfm          -> 화면 디자인/이벤트 연결 가능성
```

그 다음 줄 주변을 본다.

- 이벤트 핸들러인가?
- SQL 문자열인가?
- 상수 선언인가?
- 주석인가?
- 사용하지 않는 예전 코드인가?

검색 결과가 많을수록 "실행되는 코드인지" 확인하는 것이 중요하다.

## 10. Form에서 코드 찾기

화면에서 버튼을 봤다면 코드 찾는 순서는 다음과 같다.

1. Form Designer에서 버튼을 클릭한다.
2. Object Inspector에서 `Name`을 확인한다.
3. `Events` 탭에서 `OnClick`을 확인한다.
4. 이벤트 이름을 더블클릭한다.
5. Code Editor에서 이벤트 핸들러로 이동한다.

예:

```text
Caption = 저장
Name = btnSave
OnClick = btnSaveClick
```

이제 `btnSaveClick`을 읽으면 된다.

화면 문구만 알고 있다면 `.dfm`에서 `Caption = '저장'`을 검색하는 것도 방법이다.

## 11. 메뉴에서 코드 찾기

업무 프로그램은 상단 메뉴나 트리 메뉴로 화면을 여는 경우가 많다.

찾는 순서:

1. 메뉴 문구를 검색한다.
2. `.dfm`에서 `Caption`을 찾는다.
3. 해당 메뉴 컴포넌트의 `OnClick`을 찾는다.
4. 이벤트 핸들러에서 어떤 Form을 생성하는지 본다.

예:

```pascal
procedure TMainForm.mnuCustomerClick(Sender: TObject);
begin
  TCustomerForm.Execute;
end;
```

또는:

```pascal
CustomerForm := TCustomerForm.Create(Self);
try
  CustomerForm.ShowModal;
finally
  CustomerForm.Free;
end;
```

메뉴 문구가 DB에 저장되어 동적으로 만들어지는 시스템도 있다. 이 경우 메뉴 테이블, 권한 테이블, 화면 코드 매핑 테이블을 찾아야 한다.

## 12. SQL에서 코드 찾기

운영 이슈는 DB 테이블명이나 필드명으로 시작하는 경우가 많다.

예:

```text
CUSTOMER_ID가 잘못 저장된다.
```

검색 순서:

1. `CUSTOMER_ID` 전체 검색
2. `CUSTOMER_MST` 같은 테이블명 검색
3. 관련 Query 컴포넌트 이름 확인
4. `ParamByName('CUSTOMER_ID')` 같은 파라미터 대입 찾기
5. 저장 버튼 이벤트까지 역추적

SQL이 `.pas`에 문자열로 있을 수도 있고, `.dfm`의 Query 컴포넌트 속성에 들어 있을 수도 있다. 오래된 프로젝트에서는 SQL 파일이나 DB 프로시저에 있을 수도 있다.

## 13. 북마크와 TODO

코드를 따라가다 보면 다시 돌아와야 할 위치가 생긴다. 이때 북마크를 쓰면 좋다.

사용 예:

- 이벤트 시작점
- 실제 DB 저장 메서드
- 오류 발생 위치
- 비교해야 할 비슷한 화면

TODO 주석은 팀 규칙이 있을 때만 조심해서 쓴다.

```pascal
// TODO: 입사 후 회사 공통 검증 함수로 교체 필요
```

개인 메모성 TODO가 운영 코드에 남으면 잡음이 될 수 있다. 필요한 경우 이슈 관리 도구나 개인 노트에 적는다.

## 14. 코드 포맷과 팀 스타일

Delphi 프로젝트는 오래된 코드가 많을 수 있다. 자동 포맷을 무심코 전체 파일에 적용하면 변경량이 폭발한다.

처음에는 다음 원칙을 지킨다.

1. 내가 수정한 부분 주변만 정리한다.
2. 기존 들여쓰기 스타일을 따른다.
3. unrelated formatting을 하지 않는다.
4. `.dfm` 자동 변경이 생겼는지 확인한다.
5. 팀의 formatter/코딩 규칙이 있으면 그 기준을 따른다.

좋은 유지보수는 "내 스타일로 싹 정리"가 아니라 "필요한 곳을 정확히 고치는 것"이다.

## 15. 대형 레거시 프로젝트 탐색 요령

대형 Delphi 프로젝트에서는 다음 질문을 순서대로 던진다.

1. 이 화면은 어떤 Form인가?
2. 사용자가 누르는 버튼/메뉴의 이벤트는 무엇인가?
3. 이벤트에서 바로 처리하는가, 다른 메서드로 넘기는가?
4. DB Query는 Form에 있는가, DataModule에 있는가?
5. 공통 함수나 프레임워크를 거치는가?
6. 같은 패턴의 다른 화면이 있는가?
7. 운영 환경 설정 파일을 읽는가?
8. 권한, 회사코드, 사업장코드 같은 공통 조건이 붙는가?

특히 비슷한 화면을 찾는 것은 좋은 전략이다. 이미 동작하는 화면을 비교하면 회사 스타일을 빠르게 익힐 수 있다.

## 16. Code Insight가 안 될 때

자동 완성이나 선언 이동이 갑자기 안 될 수 있다.

확인할 것:

| 항목 | 설명 |
| --- | --- |
| 프로젝트가 정상 빌드되는가 | 빌드가 깨지면 Code Insight도 약해질 수 있다. |
| Search Path가 맞는가 | unit을 못 찾으면 선언 이동이 실패한다. |
| 패키지가 설치되어 있는가 | 외부 컴포넌트 타입을 모를 수 있다. |
| LSP가 정상 동작하는가 | IDE 재시작이 필요할 수 있다. |
| 파일 인코딩이 깨졌는가 | 오래된 코드에서 문제 가능 |

급할 때는 IDE 기능만 믿지 말고 텍스트 검색으로도 찾는다.

4. `Trim` 위에서 선언 이동을 시도한다.

## 입사 후 확인할 질문

1. 회사에서 쓰는 IDE 키맵이 기본값인가요?
2. 코드 검색은 IDE 검색을 쓰나요, 외부 검색 도구를 쓰나요?
3. 공통 함수/공통 unit 목록이 정리되어 있나요?
4. 화면과 메뉴 코드 매핑 문서가 있나요?
5. SQL은 코드에 있나요, 파일/DB 프로시저/리포트 도구에 있나요?

## 자주 막히는 지점

- 이벤트 시작점을 찾지 못하고 전체 파일을 위에서부터 읽는다.
- `.dfm`에 있는 Caption/이벤트 연결을 검색하지 않는다.
- 검색 결과가 주석인지 실제 코드인지 구분하지 않는다.
- 자동 완성이 안 되면 IDE가 고장났다고만 생각한다.
- 전체 파일 자동 포맷으로 불필요한 변경을 만든다.
- 같은 패턴의 기존 화면을 찾아보지 않는다.
