# 패키지, 라이브러리, 외부 컴포넌트

> 작성 기준일: 2026-05-19  
> 대상 독자: 기존 Delphi 프로젝트를 열었을 때 패키지/컴포넌트 오류를 만나는 사람  
> 목표: `.dpk`, `.bpl`, `.dcp`, design-time package, runtime package, Search Path 문제를 구분한다.

## 1. 패키지 문제는 Delphi 입문자의 첫 벽이다

기존 회사 프로젝트를 처음 열면 코드보다 먼저 이런 오류를 만날 수 있다.

```text
Package xxx.bpl not found
Class TSomeGrid not found
Unit SomeComponent was compiled with a different version
Cannot load package
File not found: xxx.dcu
```

이건 내가 Pascal 문법을 몰라서가 아니다. 개발 환경에 필요한 패키지, 라이브러리, 외부 컴포넌트가 아직 맞춰지지 않은 것이다.

Delphi 프로젝트는 IDE에 설치된 컴포넌트와 패키지 상태에 영향을 많이 받는다. 따라서 입사 초기에는 "소스 받기"만으로 끝나지 않고 "개발 환경 맞추기"가 필요하다.

## 2. 패키지란?

Delphi package는 여러 unit, 컴포넌트, 리소스를 묶는 배포/재사용 단위다.

공식 문서 기준 패키지는 `.dpk` 파일로 관리되고, 컴파일 결과로 `.bpl`, `.dcp` 같은 파일이 생성될 수 있다.

| 파일 | 의미 |
| --- | --- |
| `.dpk` | 패키지 소스 프로젝트 |
| `.pas` | 패키지에 포함된 unit |
| `.dcp` | 컴파일된 패키지 정보 |
| `.bpl` | Borland Package Library. 실행 시 로드되는 패키지 파일 |
| `.res` | 패키지 리소스 |

패키지는 DLL과 비슷한 면이 있지만 Delphi 컴포넌트/IDE와 더 밀접하게 연결된다.

## 3. Design-time package와 Run-time package

패키지는 크게 두 성격으로 나뉜다.

| 구분 | 역할 | 예 |
| --- | --- | --- |
| Design-time package | IDE에서 컴포넌트를 Tool Palette에 보이게 함 | 커스텀 그리드 컴포넌트 설치 |
| Run-time package | 프로그램 실행 시 필요한 코드 제공 | 공통 로직 BPL |

Design-time package는 개발자 IDE에 필요하다. 실행 파일을 쓰는 일반 사용자에게는 필요 없을 수 있다.

Run-time package는 실행 시 필요할 수 있다. 프로그램이 해당 BPL을 참조한다면 운영 PC에도 맞는 BPL이 있어야 한다.

처음에는 이렇게 구분한다.

```text
IDE에서 Form을 열 때 필요한가? -> Design-time 가능성
EXE 실행할 때 필요한가? -> Run-time 가능성
```

## 4. `.dpk` 파일 읽기

패키지 프로젝트 파일은 대략 이런 모양이다.

```pascal
package CommonControls;

requires
  rtl,
  vcl;

contains
  MyGrid in 'MyGrid.pas',
  MyButton in 'MyButton.pas';

end.
```

읽는 법:

| 구역 | 의미 |
| --- | --- |
| `package` | 패키지 이름 |
| `requires` | 이 패키지가 의존하는 다른 패키지 |
| `contains` | 이 패키지에 포함된 unit |

패키지 오류가 나면 `requires`와 `contains`를 확인한다. 빠진 의존 패키지나 누락된 unit이 있을 수 있다.

## 5. `.bpl` 파일

`.bpl`은 Borland Package Library다. 역사적 이름이 남아 있지만 현대 Delphi에서도 쓰인다.

런타임 패키지를 사용하면 EXE 실행 시 BPL이 필요할 수 있다.

오류 예:

```text
The program can't start because CommonControls.bpl is missing
```

확인할 것:

1. BPL 파일이 있는가?
2. EXE와 같은 폴더 또는 PATH에서 찾을 수 있는가?
3. Win32/Win64 비트 수가 맞는가?
4. 같은 버전으로 빌드된 BPL인가?
5. Debug/Release BPL을 섞지 않았는가?

## 6. `.dcp` 파일

`.dcp`는 Delphi Compiled Package다. 컴파일러가 패키지의 심볼 정보를 참조할 때 사용한다.

패키지를 사용하는 다른 프로젝트는 `.dcp`를 필요로 할 수 있다.

오류 예:

```text
Required package 'CommonControls' not found
```

또는:

```text
Cannot find CommonControls.dcp
```

이 경우 DCP output directory, Library Path, 패키지 빌드 순서를 확인한다.

## 7. 외부 컴포넌트

외부 컴포넌트는 Delphi 기본 VCL이 아닌, 회사 자체 제작 또는 서드파티 라이브러리로 제공되는 컴포넌트다.

예:

- 고급 Grid 컴포넌트
- 리포트/출력 컴포넌트
- 차트 컴포넌트
- 스킨/UI 컴포넌트
- 바코드/QR 컴포넌트
- 엑셀/문서 처리 컴포넌트
- DB 연결 보조 컴포넌트
- 회사 공통 화면 프레임워크

외부 컴포넌트가 없으면 Form Designer가 화면을 열지 못할 수 있다.

오류 예:

```text
Class TAdvStringGrid not found
Class TcxGrid not found
Error reading Form1.dfm
```

이 경우 `.dfm`에는 컴포넌트 정보가 있는데 IDE가 해당 클래스를 모르는 상태다.

## 8. GetIt Package Manager

Delphi IDE에는 GetIt Package Manager가 있다. 공식 CE 설치 흐름에서도 Web 기반 GetIt installer가 언급된다.

GetIt은 일부 패키지와 라이브러리를 IDE에서 설치할 수 있게 해준다. 다만 회사 프로젝트에 필요한 모든 컴포넌트가 GetIt에 있는 것은 아니다.

회사 프로젝트에서는 보통 다음 중 하나다.

- 사내 공유 폴더에 설치 파일이 있다.
- 특정 서드파티 컴포넌트 라이선스를 별도로 받는다.
- 소스 형태 패키지를 직접 빌드한다.
- NuGet/npm 같은 방식이 아니라 수동 설치 절차가 있다.

입사 후에는 임의로 최신 버전을 설치하지 않는다. 회사 프로젝트가 요구하는 정확한 버전이 중요하다.

## 9. 설치 순서가 중요한 이유

패키지는 서로 의존한다.

예:

```text
CommonCore.dpk
-> CommonUI.dpk
-> ERPControls.dpk
-> ERPClient.dproj
```

아래쪽 프로젝트를 빌드하려면 위쪽 패키지가 먼저 빌드/설치되어야 한다.

설치 순서가 틀리면 다음 오류가 난다.

- required package not found
- unit not found
- compiled with a different version
- cannot load package

사내 개발환경 문서가 있다면 그대로 따른다. 없으면 선배 개발자에게 빌드 순서를 물어보고 직접 정리해둔다.

## 10. Search Path, Library Path, Browsing Path

패키지와 라이브러리 문제는 경로 문제와 자주 섞인다.

| 경로 | 용도 |
| --- | --- |
| Search Path | 현재 프로젝트 컴파일 시 unit 검색 |
| Library Path | IDE/컴파일러가 공통 라이브러리 검색 |
| Browsing Path | 코드 탐색/선언 이동 |
| Package output directory | BPL 등 패키지 결과물 위치 |
| DCP output directory | DCP 결과물 위치 |
| Debug DCU Path | 디버깅 가능한 DCU 검색 |

공식 AddOptionPath 문서도 Delphi의 Library Path, Package output directory, DCP output directory, Browsing path, Debug DCU path 등을 구분한다.

Code Insight가 안 되거나 빌드는 되는데 선언 이동이 안 되는 경우 Browsing Path 문제일 수도 있다.

## 11. "compiled with a different version" 오류

자주 만나는 오류다.

예:

```text
Unit CommonUtils was compiled with a different version of System.SysUtils
```

가능한 원인:

- 다른 Delphi 버전에서 빌드한 `.dcu`를 참조한다.
- Debug/Release 산출물이 섞였다.
- Win32/Win64 산출물이 섞였다.
- 오래된 패키지 산출물이 남아 있다.
- Library Path가 엉뚱한 폴더를 먼저 본다.

대응:

1. Clean 한다.
2. 관련 `.dcu`, `.dcp`, `.bpl` 산출물 위치를 확인한다.
3. 올바른 Delphi 버전에서 전체 패키지를 다시 빌드한다.
4. Search Path/Library Path 순서를 확인한다.
5. 같은 이름의 파일이 여러 경로에 있는지 찾는다.

## 12. Form Designer가 안 열릴 때

기존 Form을 열었는데 오류가 나면 당황하기 쉽다.

주요 원인:

| 증상 | 원인 후보 |
| --- | --- |
| Class xxx not found | 컴포넌트 미설치 |
| Error reading xxx.dfm | `.dfm`의 컴포넌트를 IDE가 해석 못함 |
| Package xxx not found | design-time package 미설치 |
| Access violation while loading form | 컴포넌트 초기화 문제 |
| Property xxx does not exist | 컴포넌트 버전 불일치 |

이때 `.dfm`을 무작정 고치지 않는다. 필요한 컴포넌트를 먼저 설치하거나 버전을 맞춘다.

## 13. Runtime package 설정

프로젝트 옵션에는 runtime package 사용 여부와 package 목록이 있을 수 있다.

공식 Custom Packages 문서에서는 custom runtime package를 애플리케이션에서 사용하려면 `Project > Options`에서 Runtime Packages에 패키지 이름을 추가한다고 설명한다.

runtime package 사용 여부에 따라 배포 방식이 달라진다.

| 설정 | 결과 |
| --- | --- |
| runtime package 미사용 | EXE가 커질 수 있지만 배포 파일이 단순할 수 있음 |
| runtime package 사용 | EXE 외에 필요한 BPL을 함께 배포해야 함 |

회사 프로젝트가 어떤 방식을 쓰는지 확인한다.

## 14. 외부 컴포넌트 버전 관리

외부 컴포넌트는 버전이 다르면 문제가 생길 수 있다.

예:

- 개발자 A는 Grid v1.5
- 개발자 B는 Grid v2.0
- 운영 빌드 PC는 Grid v1.4

이 상태에서는 Form Designer가 속성을 다르게 저장하거나, 빌드 결과가 달라질 수 있다.

확인할 것:

1. 컴포넌트 이름
2. 정확한 버전
3. 라이선스 키/계정
4. 설치 파일 위치
5. 설치 순서
6. Win32/Win64 지원 여부
7. Delphi 버전 호환 여부

## 15. 회사 공통 라이브러리

회사 프로젝트에는 자체 공통 라이브러리가 있을 수 있다.

예:

- 공통 메시지 함수
- 공통 DB 연결
- 권한 체크
- 로그 기록
- 공통 검색 화면
- 공통 그리드 유틸
- 리포트 출력
- 엑셀 내보내기

이런 라이브러리는 패키지, 소스 unit, DLL, BPL 등 다양한 형태일 수 있다.

입사 초기에는 공통 라이브러리 목록과 역할을 따로 정리해두면 좋다.

## 16. 개발환경 인수인계 체크리스트

기존 Delphi 프로젝트를 받으면 다음을 확인한다.

1. Delphi/RAD Studio 정확한 버전
2. 에디션
3. Target Platform
4. 외부 컴포넌트 목록
5. 컴포넌트 버전
6. 설치 파일 위치
7. 설치 순서
8. 사내 패키지 빌드 순서
9. Library Path/Search Path 설정
10. BPL/DCP output directory
11. 빌드 산출물 정리 방법
12. 배포에 필요한 runtime package 목록

## 바로 해볼 실습

1. 예제 프로젝트의 Project Options에서 runtime package 관련 설정 위치를 찾아본다.
2. 프로젝트 폴더에서 `.dpk`, `.bpl`, `.dcp`, `.dcu` 확장자를 검색해본다.
3. README나 사내 문서가 있다면 외부 컴포넌트 목록을 적어본다.
4. Tool Palette에 설치된 컴포넌트 카테고리를 훑어본다.
5. Form Designer에서 Non-Visual Component와 Visual Component를 구분해본다.

## 입사 후 확인할 질문

1. 외부 컴포넌트 목록과 버전 문서가 있나요?
2. 사내 패키지 빌드 순서가 있나요?
3. design-time package와 runtime package를 구분해 관리하나요?
4. BPL을 운영 PC에 배포하나요?
5. 빌드 PC의 Delphi/컴포넌트 버전은 개발자 PC와 같나요?
6. 컴포넌트 라이선스 키는 어떻게 관리하나요?

## 자주 막히는 지점

- 패키지 미설치를 코드 오류로 착각한다.
- 최신 컴포넌트를 설치해 기존 프로젝트와 버전이 안 맞는다.
- Win32/Win64 BPL을 섞는다.
- `.dfm`에서 Class not found가 나자마자 직접 지우려 한다.
- DCP/BPL output directory를 모른다.
- 같은 이름의 `.dcu`가 여러 경로에 있는 것을 놓친다.
