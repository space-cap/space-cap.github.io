# 디버깅 기본기

> 작성 기준일: 2026-05-19  
> 대상 독자: Delphi IDE에서 코드를 멈춰 세우고 값을 확인하는 방법을 익히려는 사람  
> 목표: 브레이크포인트, Step 실행, Watch, Local Variables, Call Stack을 이용해 오류를 추적한다.

## 1. 디버깅은 추측을 줄이는 기술이다

Delphi 유지보수에서 가장 위험한 말은 "아마 여기일 것 같습니다"다. 디버깅은 그 "아마"를 줄이는 일이다.

버튼을 눌렀을 때 실제로 어떤 코드가 실행되는지, 변수 값이 언제 바뀌는지, 예외가 어디서 시작되는지를 IDE 안에서 확인한다.

기본 흐름은 이렇다.

```text
브레이크포인트 설정
-> 프로그램 실행
-> 코드가 멈춤
-> 변수 값 확인
-> 한 줄씩 실행
-> 호출 흐름 확인
-> 원인 위치 좁히기
```

처음에는 디버거 기능을 전부 외울 필요가 없다. `Breakpoint`, `Step Over`, `Step Into`, `Watch`, `Local Variables`, `Call Stack`만 익혀도 실무 대응력이 크게 올라간다.

## 2. Debug 빌드와 Release 빌드

디버깅은 보통 `Debug` 빌드 구성에서 한다.

| 구성 | 용도 |
| --- | --- |
| Debug | 개발 중 디버깅용. 디버그 정보 포함, 최적화 낮음 |
| Release | 배포용. 최적화 적용 가능, 디버깅 정보 제한 가능 |

공식 문서 기준 RAD Studio IDE는 기본적으로 `Base`, `Debug`, `Release` 빌드 구성을 제공한다. Debug와 Release는 서로 다른 컴파일 옵션을 가질 수 있다.

디버깅이 잘 안 되면 먼저 확인한다.

1. 현재 Build Configuration이 `Debug`인가?
2. Target Platform이 맞는가? Win32와 Win64를 혼동하지 않았는가?
3. 내가 실행한 파일이 방금 빌드한 파일인가?
4. 디버그 정보가 생성되도록 설정되어 있는가?

## 3. 브레이크포인트

브레이크포인트는 프로그램을 멈출 위치다.

공식 IDE Tutorial은 코드 줄 왼쪽 여백을 클릭해서 브레이크포인트를 설정하고, 실행 중 해당 줄에 도달하면 IDE가 멈춘다고 설명한다. 실행 가능한 줄에만 설정할 수 있다.

설정 방법:

1. Code Editor에서 멈추고 싶은 줄을 찾는다.
2. 줄 왼쪽 여백을 클릭한다.
3. 빨간 점 또는 표시가 생기는지 확인한다.
4. 프로그램을 실행한다.
5. 해당 코드가 실행되면 IDE가 멈춘다.

좋은 브레이크포인트 위치:

| 위치 | 이유 |
| --- | --- |
| 버튼 `OnClick` 첫 줄 | 이벤트가 실제로 연결되어 있는지 확인 |
| 입력값 검증 직전 | 화면 값 확인 |
| SQL 파라미터 대입 직후 | DB에 어떤 값이 들어가는지 확인 |
| `ExecSQL` 또는 `Open` 직전 | 실행 SQL 확인 |
| 예외가 발생하는 줄 근처 | 원인 좁히기 |

## 4. 브레이크포인트가 안 걸릴 때

브레이크포인트가 회색이거나 실행해도 멈추지 않는다면 다음을 확인한다.

| 확인 항목 | 설명 |
| --- | --- |
| 실행되는 코드가 맞는가 | 비슷한 Form/메서드가 여러 개일 수 있다. |
| 이벤트 연결이 맞는가 | Object Inspector의 `OnClick` 확인 |
| Debug 빌드인가 | Release에서는 디버깅 정보가 부족할 수 있다. |
| 소스와 EXE가 일치하는가 | 오래된 실행 파일을 실행 중일 수 있다. |
| 조건부 컴파일인가 | `{$IFDEF}` 때문에 해당 코드가 빠졌을 수 있다. |
| 패키지/BPL 코드인가 | 별도 패키지 디버그 정보가 필요할 수 있다. |

처음에는 "디버거가 이상하다"보다 "내가 생각한 코드가 실행되지 않는다"를 먼저 의심하는 편이 좋다.

## 5. 실행과 중지

자주 쓰는 실행 명령:

| 명령 | 의미 |
| --- | --- |
| Run | 프로그램 실행 |
| Pause | 실행 중인 프로그램 일시 중지 |
| Stop | 디버깅 종료 |
| Reset | 디버그 세션 강제 종료 성격 |

실행 중인 프로그램을 닫지 않고 다시 빌드하려 하면 파일이 잠겨 오류가 날 수 있다. 특히 EXE가 실행 중이면 새 EXE로 덮어쓰지 못한다.

## 6. Step Over, Step Into, Step Out

코드가 브레이크포인트에서 멈췄다면 한 줄씩 실행할 수 있다.

| 명령 | 의미 | 언제 쓰나 |
| --- | --- | --- |
| Step Over | 현재 줄 실행 후 다음 줄로 이동. 호출한 메서드 안으로 들어가지 않음 | 전체 흐름을 빠르게 볼 때 |
| Step Into | 호출한 메서드 안으로 들어감 | 내부 로직을 확인할 때 |
| Step Out | 현재 메서드를 빠져나감 | 너무 깊이 들어갔을 때 |

예:

```pascal
ValidateInput;
SaveCustomer;
RefreshGrid;
```

`Step Over`를 누르면 각 메서드를 한 줄 단위로 넘어간다. `ValidateInput` 내부를 보고 싶다면 그 줄에서 `Step Into`를 누른다.

처음에는 `Step Into`를 너무 많이 쓰면 라이브러리 코드까지 들어가 길을 잃는다. 업무 메서드 안으로 들어갈 때만 쓰는 습관이 좋다.

## 7. Local Variables

`Local Variables` 창은 현재 메서드 안의 지역 변수 값을 보여준다.

예:

```pascal
procedure TMainForm.btnSaveClick(Sender: TObject);
var
  CustomerName: string;
begin
  CustomerName := Trim(edtName.Text);
  SaveCustomer(CustomerName);
end;
```

브레이크포인트가 이 메서드 안에 걸리면 `CustomerName` 값을 Local Variables에서 확인할 수 있다.

확인할 것:

- 문자열이 비어 있는가?
- 숫자가 예상보다 0인가?
- 객체가 `nil`인가?
- 날짜 값이 이상한가?
- Boolean 값이 예상과 반대인가?

## 8. Watch

`Watch`는 내가 지정한 표현식을 계속 감시하는 기능이다.

예:

```pascal
edtName.Text
CustomerId
Query.ParamByName('customer_id').AsString
```

변수 위에서 Watch에 추가하거나, Watch 창에서 직접 표현식을 입력한다.

주의할 점:

- Watch 표현식이 함수 호출을 포함하면 부작용이 생길 수 있다.
- DB Query나 객체 상태에 따라 평가 자체가 오류를 낼 수 있다.
- 값이 보이지 않는다고 해서 항상 변수가 없는 것은 아니다. 디버그 정보나 최적화 문제일 수 있다.

공식 Debugger Options에는 Watch 평가 시 side effect와 function call 허용 여부 같은 옵션이 있다. 초보자는 Watch에 복잡한 함수 호출을 넣지 않는 편이 안전하다.

## 9. Evaluate/Modify

`Evaluate/Modify`는 실행 중 특정 표현식 값을 확인하거나 바꾸는 기능이다.

예:

```pascal
CustomerName
edtName.Text
```

사용 예:

- 조건문에 들어가기 전 값을 확인한다.
- 테스트를 위해 Boolean 값을 임시로 바꿔본다.
- 특정 분기를 강제로 태워본다.

하지만 실무에서는 조심해야 한다. 실행 중 값을 바꾸면 실제 프로그램 상태가 바뀐다. 특히 DB 트랜잭션, 파일 처리, 외부 장비 제어 중에는 함부로 수정하지 않는다.

## 10. Call Stack

`Call Stack`은 지금 코드가 어떤 호출 흐름을 거쳐 들어왔는지 보여준다.

예:

```text
TMainForm.SaveCustomer
TMainForm.btnSaveClick
TApplication.ProcessMessage
...
```

읽는 법:

| 위치 | 의미 |
| --- | --- |
| 맨 위 | 현재 실행 중인 메서드 |
| 아래쪽 | 이 메서드를 호출한 이전 흐름 |

Call Stack은 특히 이런 상황에서 유용하다.

- 같은 메서드가 여러 화면에서 호출된다.
- 공통 함수에서 오류가 발생했는데 어느 화면에서 왔는지 모른다.
- 예외 메시지는 같지만 호출 경로가 다르다.
- 이벤트가 예상과 다른 순서로 실행된다.

## 11. 예외 디버깅

예외가 발생하면 IDE가 해당 위치에서 멈출 수 있다.

예:

```pascal
raise Exception.Create('고객명이 없습니다.');
```

또는 DB 오류:

```text
Violation of PRIMARY KEY constraint
Invalid column name
Connection is not established
```

예외를 만나면 바로 코드를 고치지 말고 다음을 본다.

1. 예외 메시지 원문
2. 예외가 발생한 줄
3. Call Stack
4. 관련 변수 값
5. DB 파라미터 값
6. 재현 조건

예외 메시지는 그대로 복사해 두는 것이 좋다. 한 글자 차이가 원인 파악에 중요할 때가 있다.

## 12. DB 코드 디버깅

Delphi 업무 프로그램의 디버깅은 DB 코드에서 많이 일어난다.

자주 확인할 것:

| 항목 | 확인 이유 |
| --- | --- |
| SQL.Text | 실제 실행 SQL 확인 |
| ParamByName 값 | 파라미터가 제대로 들어갔는지 |
| Connection | 개발/운영 DB 혼동 방지 |
| Transaction | Commit/Rollback 흐름 |
| Query.Active | 조회 결과가 열렸는지 |
| RecordCount | 결과 건수 |
| FieldByName 값 | 컬럼 값 확인 |

예:

```pascal
Query.SQL.Text := 'select * from customer where customer_id = :customer_id';
Query.ParamByName('customer_id').AsString := CustomerId;
Query.Open;
```

브레이크포인트는 `Open` 직전에 걸고 `CustomerId`, `Query.SQL.Text`, 파라미터 값을 확인한다.

운영 DB에 연결된 상태에서 디버깅하면 매우 위험하다. 입사 초기에는 개발 DB와 운영 DB 구분을 반드시 확인한다.

## 13. 화면 이벤트 순서 디버깅

VCL Form에는 여러 이벤트가 있다.

예:

```text
OnCreate
OnShow
OnActivate
OnEnter
OnChange
OnClick
OnClose
```

이벤트 순서가 예상과 다르면 버그가 생긴다.

예:

- Form이 보이기 전에 DB 조회가 실행된다.
- `OnChange`가 초기화 중에도 실행된다.
- `OnShow`에서 매번 데이터를 다시 조회해 느려진다.
- `OnClose`에서 자원을 해제하지 않는다.

이럴 때는 각 이벤트 첫 줄에 브레이크포인트를 걸고 실제 순서를 확인한다.

## 14. 조건부 브레이크포인트

반복문 안에서 특정 값일 때만 멈추고 싶을 수 있다.

예:

```pascal
for I := 0 to List.Count - 1 do
begin
  ProcessItem(List[I]);
end;
```

`I = 120`일 때만 멈추고 싶다면 조건부 브레이크포인트를 사용한다. IDE의 브레이크포인트 속성에서 조건을 설정할 수 있다.

자주 쓰는 조건:

```pascal
CustomerId = 'C001'
I = 120
Quantity < 0
Assigned(Customer)
```

조건부 브레이크포인트는 편하지만 조건 평가가 느릴 수 있다. 대량 반복문에서는 성능에 주의한다.

## 15. 로그와 디버거를 같이 쓰기

디버거는 개발 PC에서 강력하지만, 운영 환경에서는 브레이크포인트를 걸 수 없다. 그래서 로그도 중요하다.

디버깅 중 확인한 내용을 로그로 남겨야 할지 판단한다.

로그로 남기면 좋은 것:

- 사용자 ID
- 화면 ID
- 주요 입력값
- SQL 실행 전 핵심 파라미터
- 예외 메시지와 Call Stack
- 외부 연동 요청/응답 일부

남기면 안 되는 것:

- 비밀번호
- 주민번호/민감 개인정보
- 카드번호
- 운영 DB 접속 정보
- 과도한 SQL 전체 로그

## 16. 디버깅 체크리스트

문제가 생기면 다음 순서로 좁힌다.

1. 재현 절차를 정확히 적는다.
2. 어떤 화면/버튼/메뉴인지 확인한다.
3. Object Inspector에서 이벤트 연결을 찾는다.
4. 이벤트 첫 줄에 브레이크포인트를 건다.
5. 실행해서 실제로 멈추는지 확인한다.
6. 입력값과 변수 값을 본다.
7. 호출하는 메서드를 Step Into로 따라간다.
8. DB 실행 직전 값을 확인한다.
9. 예외가 발생하면 메시지와 Call Stack을 저장한다.
10. 원인 후보를 하나씩 제거한다.

## 입사 후 확인할 질문

1. 회사에서는 개발 DB와 운영 DB를 어떻게 구분하나요?
2. 디버깅 중 운영 DB에 연결되지 않도록 막는 장치가 있나요?
3. 예외 로그는 어디에 남나요?
4. 공통 오류 처리 함수가 있나요?
5. 패키지/BPL 코드도 디버깅할 수 있게 디버그 정보가 제공되나요?
6. 원격 고객 PC 문제는 어떤 방식으로 재현하나요?

## 자주 막히는 지점

- 브레이크포인트가 안 걸리는데 이벤트 연결을 확인하지 않는다.
- Release 구성으로 디버깅하려 한다.
- Win32로 빌드했는데 Win64 EXE를 실행한다.
- Watch에 부작용 있는 함수를 넣는다.
- 운영 DB에 연결된 상태로 저장/삭제 코드를 Step 실행한다.
- Call Stack을 보지 않아 호출 경로를 놓친다.
