# 빌드, 실행, 배포 기본

> 작성 기준일: 2026-05-19  
> 대상 독자: Delphi 프로젝트를 빌드하고 실행 파일 위치와 배포 흐름을 이해하려는 사람  
> 목표: Debug/Release, Target Platform, Compile/Build/Clean, output 경로, 배포 전 체크리스트를 익힌다.

## 1. 빌드는 "코드를 EXE로 만드는 계약"이다

Delphi IDE에서 코드를 고치는 것과 실제 실행 파일이 만들어지는 것은 다른 일이다.

빌드 설정이 다르면 같은 코드도 다른 결과가 나온다.

```text
소스 코드
-> Build Configuration
-> Target Platform
-> Compiler Options
-> Search Path
-> Packages
-> EXE/DLL/BPL 생성
```

처음에는 다음 네 가지를 계속 확인한다.

1. 현재 프로젝트가 맞는가?
2. Debug인가 Release인가?
3. Win32인가 Win64인가?
4. 실행 파일이 어디에 만들어지는가?

## 2. Compile, Build, Clean

IDE 메뉴나 Project Manager에서 자주 보는 명령이다.

| 명령 | 의미 | 언제 쓰나 |
| --- | --- | --- |
| Compile | 변경된 파일 중심으로 컴파일 | 빠르게 확인할 때 |
| Build | 프로젝트 전체를 다시 빌드 | 설정 변경 후, 배포 전 |
| Clean | 이전 빌드 산출물 제거 | 이상한 빌드 캐시 문제 의심 시 |
| Run | 빌드 후 실행 | 개발 중 테스트 |

문제가 잘 안 풀릴 때는 `Clean -> Build`를 해본다. 오래된 `.dcu`나 산출물이 남아 이상한 결과를 만드는 경우가 있다.

## 3. Build Configuration

공식 문서 기준 RAD Studio는 기본적으로 `Base`, `Debug`, `Release` 빌드 구성을 제공한다. 각 구성은 서로 다른 프로젝트 옵션을 가질 수 있다.

| 구성 | 용도 |
| --- | --- |
| Base | 공통 설정의 기반 |
| Debug | 개발/디버깅용 |
| Release | 배포/운영용 |

Debug와 Release에서 다를 수 있는 것:

- 최적화 여부
- 디버그 정보 생성 여부
- 조건부 define
- output directory
- runtime package 사용 여부
- 컴파일러 경고/힌트 설정

실무에서는 Debug에서 잘 되는데 Release에서만 안 되는 문제가 있다. 최적화, 조건부 컴파일, 초기화되지 않은 변수, 경로 차이를 확인한다.

## 4. Target Platform

Target Platform은 어떤 플랫폼용으로 빌드할지 정한다.

공식 Target Platforms 문서에 따르면 VCL 애플리케이션은 Win32와 Win64 같은 Windows 대상 플랫폼을 지원한다.

업무용 VCL 프로그램에서는 보통 다음을 만난다.

| Target Platform | 의미 |
| --- | --- |
| Windows 32-bit / Win32 | 32비트 Windows 실행 파일 |
| Windows 64-bit / Win64 | 64비트 Windows 실행 파일 |

Win32와 Win64는 생각보다 큰 차이를 만든다.

| 차이 | 영향 |
| --- | --- |
| 외부 DLL | 32비트 EXE는 32비트 DLL만 로드 가능 |
| DB 드라이버 | ODBC/클라이언트 드라이버 비트 수 일치 필요 |
| COM/ActiveX | 등록된 비트 수 확인 필요 |
| 메모리 | 64비트가 더 넓은 주소 공간 사용 |
| 포인터/정수 변환 | 오래된 코드에서 오류 가능 |

입사 초기에는 회사가 기본으로 쓰는 Target Platform을 반드시 확인한다.

## 5. Active Project 확인

Project Group에 여러 프로젝트가 있으면 현재 활성 프로젝트가 무엇인지 확인해야 한다.

예:

```text
ERPClient.dproj
CommonPackage.dproj
ReportTool.dproj
MigrationTool.dproj
```

여기서 `CommonPackage`를 실행하려고 하면 안 된다. 실행해야 할 것은 보통 클라이언트 EXE 프로젝트다.

Project Manager에서 확인할 것:

1. 굵게 표시되거나 활성화된 프로젝트
2. Run 대상 프로젝트
3. Build 대상 프로젝트
4. Project Group 빌드 순서

## 6. Output Directory

빌드 결과물이 어디에 생기는지 알아야 한다.

흔한 구조:

```text
Win32\Debug\
Win32\Release\
Win64\Debug\
Win64\Release\
```

하지만 회사 프로젝트는 별도 output directory를 쓸 수 있다.

예:

```text
bin\debug\
bin\release\
deploy\
..\Output\Win32\
```

확인 위치:

```text
Project > Options > Building > Delphi Compiler
```

IDE 버전과 프로젝트 유형에 따라 메뉴 구조는 조금 다를 수 있다.

## 7. DCU Output Directory

`.dcu`는 Delphi unit이 컴파일된 결과물이다.

소스 `.pas`가 컴파일되면 `.dcu`가 생기고, 최종 EXE 빌드에 사용된다.

주의할 점:

- 오래된 `.dcu`가 남아 있으면 최신 소스와 다른 동작을 할 수 있다.
- DCU output 경로가 섞이면 다른 프로젝트의 산출물을 참조할 수 있다.
- Debug/Release, Win32/Win64 산출물을 분리하는 것이 좋다.

문제가 이상하게 꼬이면 Clean 후 Build를 시도한다.

## 8. Search Path와 Library Path

Delphi가 unit을 찾는 경로가 있다.

| 경로 | 의미 |
| --- | --- |
| Search Path | 현재 프로젝트에서 unit을 찾는 경로 |
| Library Path | IDE/컴파일러가 공통 라이브러리를 찾는 경로 |
| Browsing Path | 코드 탐색/선언 이동에 쓰이는 경로 |
| Debug DCU Path | 디버깅 가능한 DCU 경로 |

공식 AddOptionPath 문서에는 Delphi personality에서 Library Path, Package output directory, DCP output directory, Browsing path, Debug DCU path 같은 옵션 경로가 구분되어 있다.

실무에서 자주 보는 오류:

```text
File not found: 'CommonUtils.dcu'
Unit xxx was compiled with a different version of yyy
Cannot resolve unit name
```

이런 오류는 코드 오타가 아니라 경로/버전 문제일 수 있다.

## 9. 빌드 메시지 읽기

빌드하면 `Messages` 창에 결과가 나온다.

| 메시지 | 의미 |
| --- | --- |
| Hint | 참고. 사용하지 않는 변수 등 |
| Warning | 빌드는 되지만 위험한 부분 |
| Error | 빌드 실패 |
| Fatal | 컴파일을 계속할 수 없는 오류 |

처음에는 맨 위 오류보다 맨 처음 발생한 실제 Error를 찾는다. 뒤쪽 오류는 앞 오류 때문에 연쇄적으로 난 것일 수 있다.

자주 보는 오류:

| 오류 유형 | 원인 후보 |
| --- | --- |
| unit not found | Search Path, 파일 누락, 패키지 미설치 |
| identifier not found | uses 누락, 오타, 조건부 컴파일 |
| incompatible types | 타입 불일치 |
| unsatisfied forward declaration | 선언만 있고 구현 없음 |
| resource not found | `.res`, `.dfm`, 이미지/리소스 누락 |
| package not found | BPL/DCP 경로 문제 |

## 10. 조건부 컴파일

Delphi 코드에는 조건부 컴파일이 있을 수 있다.

```pascal
{$IFDEF DEBUG}
  Log('Debug mode');
{$ENDIF}
```

또는:

```pascal
{$IFDEF WIN64}
  // 64비트 전용 코드
{$ENDIF}
```

Debug/Release, Win32/Win64, 회사별 define에 따라 코드가 포함되거나 빠질 수 있다.

빌드 설정에서 conditional defines를 확인한다. 같은 소스인데 PC마다 다르게 동작하면 define 차이일 수 있다.

## 11. 실행 파일과 필요한 파일

Delphi는 단일 EXE로 배포되는 경우도 있지만, 항상 EXE 하나만 있으면 되는 것은 아니다.

필요할 수 있는 파일:

| 파일 | 이유 |
| --- | --- |
| `.exe` | 실행 파일 |
| `.dll` | 외부 라이브러리 |
| `.bpl` | runtime package |
| 설정 파일 | DB 접속, 환경 설정 |
| 리포트 파일 | 출력 양식 |
| 이미지/템플릿 | 화면/출력 리소스 |
| DB 드라이버 | DB 접속용 클라이언트 |

배포 전에는 실행 파일이 의존하는 파일을 확인한다.

## 12. Runtime Packages

프로젝트가 runtime package를 사용하면 실행 시 `.bpl` 파일이 필요할 수 있다.

장점:

- 여러 프로그램이 공통 패키지를 공유할 수 있다.
- EXE 크기가 줄 수 있다.
- 공통 모듈을 분리할 수 있다.

주의:

- 대상 PC에 맞는 BPL이 있어야 한다.
- BPL 버전이 안 맞으면 실행 오류가 난다.
- Win32/Win64 BPL을 혼동하면 안 된다.

runtime package는 `11_패키지_라이브러리_외부_컴포넌트.md`에서 더 자세히 다룬다.

## 13. 배포 방식

회사마다 배포 방식이 다르다.

| 방식 | 설명 |
| --- | --- |
| 수동 복사 | EXE/DLL을 공유 폴더나 고객 PC에 복사 |
| 설치 프로그램 | Inno Setup, InstallShield 등으로 설치 |
| 자동 업데이트 | 실행 시 최신 파일 다운로드 |
| 원격 접속 배포 | 고객 PC에 접속해 교체 |
| 빌드 서버 | CI/CD 또는 전용 빌드 PC에서 산출 |

입사 초기에는 배포를 직접 하지 않는 것이 좋다. 먼저 절차를 확인하고, 선배와 함께 진행한다.

## 14. 배포 전 체크리스트

배포 전 최소 확인:

1. Release 구성으로 빌드했는가?
2. Target Platform이 운영 환경과 맞는가?
3. 버전 정보가 맞는가?
4. 실행 파일 생성 시간이 최신인가?
5. 필요한 DLL/BPL/설정 파일이 포함되었는가?
6. 개발 DB 접속 정보가 남아 있지 않은가?
7. 테스트 PC에서 실행 확인했는가?
8. 변경 내역과 롤백 방법을 기록했는가?
9. 운영 반영 승인 절차를 따랐는가?

## 15. 빌드 문제 해결 순서

빌드가 실패하면 이렇게 본다.

1. Messages 창에서 첫 Error를 찾는다.
2. 오류가 코드 문법인지 경로 문제인지 구분한다.
3. Target Platform과 Build Configuration을 확인한다.
4. Search Path와 Library Path를 확인한다.
5. 외부 패키지 설치 여부를 확인한다.
6. Clean 후 Build를 시도한다.
7. 다른 개발자 PC에서도 재현되는지 확인한다.
8. 최근 `.dproj` 변경을 확인한다.

## 바로 해볼 실습

1. 예제 VCL 프로젝트를 Debug로 빌드한다.
2. 생성된 EXE 위치를 확인한다.
3. Release로 바꿔 다시 빌드한다.
4. Win32와 Win64 선택지가 있다면 각각 output 경로 차이를 본다.
5. 일부러 문법 오류를 만들고 Messages 창을 읽는다.
6. Clean 후 Build를 실행해본다.

## 입사 후 확인할 질문

1. 운영 배포는 Debug인가 Release인가요?
2. 기본 Target Platform은 Win32인가요, Win64인가요?
3. EXE output directory는 어디인가요?
4. runtime package를 사용하나요?
5. 배포에 필요한 DLL/BPL 목록이 있나요?
6. 빌드 서버나 전용 빌드 PC가 있나요?
7. 배포 전 버전 정보는 누가 갱신하나요?

## 자주 막히는 지점

- Debug EXE를 운영에 배포하려 한다.
- Win32/Win64 DLL을 섞는다.
- 현재 Active Project가 아닌 다른 프로젝트를 빌드한다.
- `.dcu` 캐시 문제를 코드 문제로 착각한다.
- Search Path 누락을 소스 누락으로 오해한다.
- 배포 파일 목록에 BPL/DLL/설정 파일을 빠뜨린다.
