# SSR과 Nuxt 입문

## 이번 장에서 배울 것

Vue 앱은 기본적으로 브라우저에서 렌더링되는 클라이언트 앱으로 만들 수 있다. 하지만 SEO, 초기 로딩 속도, 콘텐츠 중심 사이트 요구가 생기면 SSR이나 SSG를 고려하게 된다.

이번 장에서는 CSR, SSR, SSG의 차이와 Nuxt의 역할을 큰 그림으로 배운다.

---

## CSR

CSR은 Client-Side Rendering의 줄임말이다. 브라우저가 JavaScript를 내려받고 실행한 뒤 화면을 만든다.

Vite로 만든 일반 Vue SPA는 보통 CSR이다.

장점:

- 정적 파일로 배포하기 쉽다.
- 서버 구성이 단순하다.
- 로그인 후 사용하는 앱, 관리자 페이지에 잘 맞는다.

단점:

- 초기 콘텐츠가 JavaScript 실행 후 보일 수 있다.
- SEO가 중요한 페이지에서는 불리할 수 있다.
- 느린 기기나 네트워크에서 첫 화면이 늦을 수 있다.

---

## SSR

SSR은 Server-Side Rendering의 줄임말이다. 서버에서 Vue 컴포넌트를 HTML 문자열로 렌더링해 브라우저에 보낸다.

브라우저는 먼저 HTML을 빠르게 보고, 이후 Vue가 hydration 과정을 통해 인터랙션을 붙인다.

장점:

- 초기 콘텐츠가 더 빨리 보일 수 있다.
- SEO에 유리하다.
- 서버에서 초기 데이터 fetching을 처리할 수 있다.

단점:

- 서버 런타임이 필요하다.
- 배포와 캐싱 전략이 복잡해진다.
- 브라우저 전용 API 사용에 주의해야 한다.
- 서버 부하가 생길 수 있다.

---

## Hydration

Hydration은 서버에서 받은 정적 HTML에 Vue의 이벤트와 반응성을 연결하는 과정이다.

서버가 HTML을 보낸 직후에는 화면이 보일 수 있지만, 클릭 같은 상호작용은 클라이언트 JavaScript가 로드되고 hydration이 끝난 뒤 제대로 동작한다.

SSR에서 서버 HTML과 클라이언트 렌더 결과가 다르면 hydration mismatch가 발생할 수 있다.

---

## SSG

SSG는 Static Site Generation의 줄임말이다. 빌드 시점에 HTML을 미리 만들어 정적 파일로 배포한다.

문서 사이트, 블로그, 마케팅 페이지처럼 콘텐츠가 자주 바뀌지 않는 경우에 좋다.

장점:

- 정적 호스팅이 가능하다.
- 빠르고 안정적이다.
- 서버 렌더링 부하가 없다.

단점:

- 데이터가 바뀌면 다시 빌드해야 한다.
- 사용자별 동적 콘텐츠에는 맞지 않을 수 있다.

---

## CSR, SSR, SSG 비교

| 구분 | 렌더링 시점 | 추천 상황 |
| --- | --- | --- |
| CSR | 브라우저 실행 시 | 관리자 페이지, 로그인 후 앱 |
| SSR | 요청 시 서버 | SEO와 초기 로딩이 중요한 동적 페이지 |
| SSG | 빌드 시 | 문서, 블로그, 마케팅 페이지 |

처음 Vue를 배우는 단계에서는 CSR로 충분하다. 필요가 생기면 SSR/SSG를 검토한다.

---

## Nuxt란?

Nuxt는 Vue 기반의 상위 프레임워크다. Vue 앱을 SSR, SSG, 파일 기반 라우팅, 서버 API, 자동 import 등으로 확장해준다.

Nuxt는 다음을 제공한다.

- 파일 기반 라우팅
- SSR과 SSG 지원
- 서버 API 라우트
- 레이아웃 시스템
- 자동 import
- 데이터 fetching 도구
- 배포 프리셋

Vue가 UI 프레임워크라면, Nuxt는 Vue로 전체 웹 애플리케이션을 만들기 위한 애플리케이션 프레임워크에 가깝다.

---

## 언제 Nuxt를 고려할까?

다음 상황이면 Nuxt를 고려할 수 있다.

- SEO가 중요한 웹사이트
- 블로그, 문서, 마케팅 페이지
- SSR/SSG가 필요하다.
- 파일 기반 라우팅과 레이아웃 시스템이 필요하다.
- Vue로 풀스택에 가까운 앱을 만들고 싶다.

반대로 내부 관리자 페이지나 로그인 후 사용 앱은 Vite + Vue Router + Pinia 조합으로도 충분한 경우가 많다.

---

## SSR 친화 코드

SSR에서는 서버에서도 코드가 실행된다. 브라우저 전용 객체를 바로 쓰면 문제가 생긴다.

주의할 것:

```js
window
document
localStorage
sessionStorage
```

이런 코드는 클라이언트에서만 실행되도록 처리해야 한다.

Vue만 사용하는 SSR에서는 `onMounted` 안에서 브라우저 API를 사용하는 것이 기본적인 안전장치다.

```js
onMounted(() => {
  console.log(window.innerWidth)
})
```

Nuxt에서는 Nuxt가 제공하는 클라이언트 전용 처리 방식을 함께 배운다.

---

## 직접 SSR을 구현해야 할까?

Vue는 SSR API를 제공하지만, 직접 SSR 환경을 구성하는 것은 초보자에게 어렵다. 라우터, 상태 관리, 데이터 fetching, 번들링, 배포까지 고려할 것이 많다.

실무에서는 직접 구현보다 Nuxt 같은 상위 솔루션을 먼저 검토하는 것이 일반적으로 안전하다.

---

## 자주 하는 실수

### SEO가 필요 없는데 SSR을 도입함

SSR은 장점도 있지만 운영 복잡도가 있다. 내부 도구라면 CSR이 더 단순할 수 있다.

### SSR에서 window를 바로 사용함

서버에는 `window`가 없다. 브라우저 API 사용 위치를 조심한다.

### Nuxt를 Vue와 완전히 다른 것으로 생각함

Nuxt는 Vue 위에 만들어진 프레임워크다. Vue 기본기를 알면 Nuxt 학습이 훨씬 쉬워진다.

---

## 작은 실습

아래 앱에 어떤 렌더링 방식이 어울리는지 생각해보자.

- 사내 관리자 페이지
- 기술 블로그
- 쇼핑몰 상품 상세 페이지
- 로그인 후 사용하는 프로젝트 관리 도구
- 회사 소개 랜딩 페이지

각각 CSR, SSR, SSG 중 무엇이 적합한지 이유를 적어보자.

---

## 이번 장 요약

- CSR은 브라우저에서 화면을 렌더링한다.
- SSR은 서버에서 HTML을 만들고 hydration으로 인터랙션을 붙인다.
- SSG는 빌드 시점에 HTML을 미리 만든다.
- Nuxt는 Vue 기반의 애플리케이션 프레임워크로 SSR/SSG를 쉽게 다룰 수 있게 해준다.
- SSR은 필요할 때 도입해야 하며, 직접 구현보다 Nuxt를 먼저 고려하는 것이 좋다.
