# 📚 정보처리기사 대비 학습 자료: 1과목. 소프트웨어 설계
## 🌟 1장. 요구사항 확인 (Requirements Elicitation & Analysis)

### 📌 1. 요구사항 확인이란 무엇인가? (Definition)
요구사항 확인(Requirements Elicitation)은 **사용자(Stakeholders)나 이해관계자들로부터 현재 시스템이 해결해야 할 문제점, 필요 기능, 제약 조건 등을 체계적이고 빠짐없이 '발굴'하고 '추출'하는 활동**입니다.
*   **핵심:** '무엇이 필요한가?'를 알아내는 과정 그 자체입니다.
*   **중요성:** 이 단계에서 요구사항이 잘못 수집되거나 누락되면, 개발된 소프트웨어는 **사용자가 원하는 기능을 갖추지 못한 채** 실패하게 됩니다. (가장 치명적인 오류 유발 지점)

---

### 💡 2. 요구사항의 종류 (Types of Requirements)
요구사항은 그 성격과 범위를에 따라 여러 종류로 분류됩니다. 이를 구분하는 것이 분석의 핵심입니다.

| 구분 | 영문명 | 정의 | 예시 |
| :--- | :--- | :--- | :--- |
| **기능적 요구사항** (Functional) | FR | 시스템이 **반드시 수행해야 하는 기능적 동작**에 대한 명세. (System *must do* this.) | "사용자는 아이디와 비밀번호를 입력하여 로그인할 수 있어야 한다.", "시스템은 검색 결과에 대해 페이지네이션을 지원해야 한다." |
| **비기능적 요구사항** (Non-Functional) | NFR | 시스템이 **어떻게 동작해야 하는가**에 대한 품질 속성이나 제약 조건. (How *well* it must perform.) | **성능:** "동시 접속자 1,000명까지 지연 시간 3초 이내여야 한다.", **보안:** "개인정보는 암호화되어 저장되어야 한다.", **사용성:** "초보 사용자도 3분 이내에 회원가입을 완료할 수 있어야 한다." |
| **도메인 요구사항** | Domain | 특정 산업(금융, 의료 등)의 전문 용어, 프로세스, 규칙 등 배경지식. | "의료 기록은 반드시 의사 자격 인증을 거쳐야 한다.", "금융 거래는 원화(KRW)를 기준으로 한다." |
| **제약 요구사항** | Constraint | 시스템 개발 시 물리적/기술적으로 부과되는 한계점. | "반드시 레거시 DB(Oracle 11g)를 사용해야 한다.", "프로젝트 기한은 6개월을 넘길 수 없다." |

### 🛠️ 3. 요구사항 도출 및 분석 기법 (Elicitation & Analysis Techniques)

요구사항을 모으고 검증하는 대표적인 기법들입니다.

#### **① 정보 수집 기법 (Elicitation Techniques)**

*   **인터뷰 (Interview):** 이해관계자(사용자, 전문가)와 직접 만나 대화하며 정보를 얻는 가장 일반적인 방법. (✅ *장점:* 깊이 있는 이해 가능. / ⚠️ *단점:* 인터뷰어의 주관이나 질문 방식에 따라 정보가 편향될 위험.)
*   **설문 조사 (Questionnaire):** 다수의 사람들에게 표준화된 질문지를 배포하여 통계를 내는 방법. (✅ *장점:* 많은 사람에게 일괄 적용 가능. / ⚠️ *단점:* 깊이 있는 맥락 파악 불가, 답변이 형식적일 수 있음.)
*   **워크숍 (Workshop):** 여러 이해관계자를 한자리에 모아 특정 주제에 대해 토론하고 합의점을 찾아가는 회의 방식. (✅ *장점:* 다양한 시각을 한자리에서 조정 가능. / ⚠️ *단점:* 참여자 간의 갈등 관리가 어려울 수 있음.)
*   **관찰 (Observation):** 사용자가 현재 업무를 수행하는 현장을 직접 지켜보면서 불편한 지점이나 비효율적인 과정을 파악하는 방법. (✅ *장점:* 실제 업무 흐름 파악에 매우 효과적. / ⚠️ *단점:* 관찰되는 것이 실제 프로세스가 아닐 수 있음 - Hawthorne Effect.)

#### **② 요구사항 분석 및 구체화 기법 (Analysis Techniques)**

*   **프로토타입 (Prototype):** 실제와 유사한 목업(Mockup)이나 작동하는 간이 모델을 만들어 사용자에게 보여주고 피드백을 받는 방식. (가장 강력한 방법 중 하나)
*   **Use Case Diagram (유스케이스 다이어그램):** 사용자의 관점에서 시스템이 수행해야 하는 **'행위 시나리오'**를 다이어그램으로 표현합니다. 누가(Actor) 어떤 기능을(Use Case) 사용할 수 있는지를 보여줍니다.
*   **흐름도 (Flowchart) / 활동 다이어그램 (Activity Diagram):** 시스템의 **처리 과정(Process Flow)**을 순서도로 그려서 논리적 흐름이나 비즈니스 프로세스의 단계를 명확히 파악합니다.

### 🔍 4. 학습 요약 및 체크 포인트 (Self-Test)

1.  **가장 중요한 질문:** 요구사항 확인 단계에서 가장 피해야 할 함정은 무엇인가? (👉 **누락, 모호성, 불일치**가 있다.)
2.  **기능적 vs 비기능적:** "이 시스템은 빨라야 한다"는 것은 **기능적 요구사항**인가, **비기능적 요구사항**인가? (👉 **비기능적 요구사항** - 성능 측면)
3.  **기법 선택:** 만약 여러 이해관계자가 서로 다른 의견을 강력하게 주장하며 합의점을 찾아야 한다면, 어떤 기법이 가장 적합한가? (👉 **워크숍**)
4.  **도구 선택:** 사용자가 시스템을 실제로 어떻게 사용하는지 처음부터 끝까지 알고 싶다면 어떤 기법을 사용해야 하는가? (👉 **관찰**)
